# Paso 10 del Roadmap — Motor de Precios Psicológicos, Redondeo Comercial y Protección de Márgenes

Objetivo: incorporar un motor de políticas de redondeo (`PricingRoundingPolicyService`) como interceptor limpio sobre la edición masiva de precios (Paso 9 / `BulkUpdatePricesAsync`) y el recálculo de precios por confirmación de facturas de proveedor: elimina decimales imprácticos para efectivo, protege el piso de rentabilidad y garantiza coherencia Detal/Mayor. Tramo 8.182. Branch: V0.15. Entrega: work units locales en V0.15 (push/PR = decisión del mantenedor). RDD: off (clone-local). Tests: build `dotnet build CommandCenter.slnx -c Release`; carriles `--filter "FullyQualifiedName~Bulk|FullyQualifiedName~Pricing|FullyQualifiedName~Product"`.

## Specs

Fuente: pedido del mantenedor (L1, spec completa del Paso 10) + exploración L2. Supuestos marcados.

- **S1 (Servicio puro de redondeo)**: `IPricingRoundingPolicyService` (interface en `Core/Interfaces` — convención del repo; la impl `PricingRoundingPolicyService` en `Inventory.Module/Services`, stateless y sin dependencias de EF). `RoundingRuleType` { ExactMath; UsdPsychological; VesCashFriendlyInteger; VesCashFriendlyStep5; VesCashFriendlyStep10 } — granulado por sub-opción para evitar campos extra en el DTO (supuesto; la spec nombra las 3 familias). UsdPsychological: terminación más cercana entre {.99, .95, .75, .50, .25} bidireccional. VesCashFriendly*: escalones de 1 / 5 / 10 Bs.S. API pura: `Round(amount, rule, cost, marginFloorPct?, enforceFloor)` → { Matemático, Redondeado, Delta, MargenEfectivoPct }; sin efectos ni estado.
- **S2 (Bidireccional con piso de margen)**: se evalúa el escalón más cercano (hacia abajo y hacia arriba); si el redondeo hacia abajo deja `MargenEfectivo = (precio−costo)/costo×100` por debajo del piso configurado (>0 y flag activo), se descarta y se usa el siguiente escalón superior. Margen efectivo recalculado y COMPUTADO sobre el precio FINAL (no el matemático). Costo 0 o piso no configurado → guard no aplica (no-op documentado).
- **S3 (Salvaguarda Detal vs Mayor)**: tras redondear ambos canales, si Mayor ≥ Detal: se ajusta Mayor al escalón inmediato inferior (siempre que quede > costo); si no es posible → fila `IsError` con motivo (bloquea apply, consistente con el all-or-nothing de 8.181). Preview lista el ajuste/alerta.
- **S4 (Integración en el motor bulk 8.181)**: secuencia: operaciones (incl. costo) → derivaciones margen→precio vigentes → **redondeo por canal (S1/S2) → salvaguarda (S3) → validación vigente `ValidateAndCalculateProductPrices` (negativos/mayor≤detal/cap) → Bs.S canónico (8.104) calculado DESDE el USD final** → márgenes efectivos re-escritos en el plan cuando una regla ≠ ExactMath cambió el precio (consistencia matemática pedida) → persistencia/propagación existentes intactas. Preview y apply comparten el motor (consistencia 8.181 se mantiene). VesCashFriendly* en bulk: redondea el **Bs.S canónico del canal** (convertido con la tasa del día); el USD y el margen no cambian; `PriceBsS` queda en escalón amigable (supuesto; divergencia deliberada del techo estricto SOLO cuando se elige esta regla).
- **S5 (DTOs)**: `BulkPriceUpdateRequestDto` + `RetailRoundingRule`/`WholesaleRoundingRule` (default ExactMath) + `EnforceMinimumMarginFloor` (bool) + `RetailMarginFloorPct`/`WholesaleMarginFloorPct` (decimal?, por lote — supuesto v1: sin setting global; residual documentado). Preview: `BulkPriceFieldChangeDto` + `PreRoundingValue` (matemático) + `RoundingDelta`; `BulkPricePreviewRowDto` + `EffectiveRetailMarginPct`/`EffectiveWholesaleMarginPct` (nullable; solo cuando cambió el precio del canal).
- **S6 (WPF)**: `BulkPriceEditDialog`: selectores de regla por canal (Detal/Mayor), inputs de piso por canal + toggle "proteger piso de margen"; preview: columnas nuevas "Matemático", "Redondeado", "Δ Redondeo", "Nuevo Margen %" (por canal afectado); validaciones client-side (piso ≥ 0, coherente con ≥1 operación). Tests de VM (reglas enviadas en el request, columnas renderizadas, flujo preview→apply).
- **S7 (Facturas proveedor)**: regla de redondeo seleccionable en el flujo de confirmación de factura (nivel factura — supuesto v1; per-línea = residual) y aplicada en `ApplyApprovedLine` (`SupplierInvoiceService.Apply.cs:391-393`) al recalcular precios por cambio de costo; default ExactMath = comportamiento actual intacto. Tests de aplicación por regla + default.
- **S8 (Proceso y alcance)**: build 0/0; carriles + suite completa por partes; verificación independiente (reviewer); ANEXO 8.182 + `Ideas.txt` Paso 10 `[x]`; commits por work units en V0.15 + push/CI. **Deferred explícito (documentar como residual)**: switch dinámico de VesCashFriendly sobre el convertido EN VIVO en POS (display/caja) — choca con la ley Bs.S techo (8.104) y toca múltiples call sites WPF/web; el servicio queda listo para ese hook futuro. Interface en Core (no en Inventory.Module como decía la spec literal) por convención de capas del repo (supuesto).

- POS Bs.S: `ToBsSCeiling` en `ProductItemViewModel:143-156`, `PosViewModel:383-386`, carrito `CartItemViewModel:72`, web `formatters.js:295-301`; pagos ya redondean a entero con `RoundToCash` (`CheckoutViewModel.Payments.cs:30,90`). Sin switch de settings para reglas.
- Tests a espejar: `PricingCalculatorTests` ([Theory]/[InlineData] decimales), `BsPriceCeilingStandardTests`, builders `ProductBuilder` (`WithCostAndMargin/WithWholesale`), helpers bulk 8.181 (`Op/Request/RowOf/ChangeOf`, `SeedRateAsync`) y builders de preview del dialog.
