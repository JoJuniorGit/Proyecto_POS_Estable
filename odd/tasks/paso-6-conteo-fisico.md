# Paso 6 del Roadmap — Conteo físico ciego e inventario rotativo con escáner móvil

Objetivo: sesiones de conteo físico (`StockCountSession`/`StockCountItem`) con modo CIEGO en el escáner Web/móvil (sin mostrar la existencia teórica), cálculo de discrepancias al cerrar (sobrantes/faltantes + valor) y aplicación aprobada que ajusta stock con trazabilidad completa en `StockMovement` (Fase 3 del roadmap, consumo directo del Kardex del Paso 5). Tramo 8.180. Branch: V0.15. Entrega: work units locales (push/PR = decisión del mantenedor). RDD: off (clone-local). Tests: build `dotnet build CommandCenter.slnx -c Release`; carriles `--filter "FullyQualifiedName~StockCount|FullyQualifiedName~Inventory|FullyQualifiedName~Categor"`; web `npm test` + `npm run lint` en `Web.Frontend`.

## Specs

Fuente: `docs/Ideas.txt` Paso 6 (sincronizado 2026-10-13) + pedido del mantenedor ("continua con p6"). Supuestos marcados.

- **S1 (Modelo)**: `StockCountSession` (Name ≤80, `StockCountStatus {Open, Closed, Applied, Cancelled}` string(32), `ScopeCategoryId` int? (subtárbol; null = todos), `CreatedByUserId`, timestamps `ClosedAt`/`AppliedAt` + `AppliedByUserId`, `Notes` ≤300, token `xmin`) + `StockCountItem` (FK sesión Cascade, FK producto Restrict, `CountedQuantity` 18,3, `UpdatedAt`, y al cerrar: `TheoreticalStock` 18,3 + `UnitCostUSD` 18,4 nullable). Único `(SessionId, ProductId)`. `StockMovement` + `StockMovements_Archive` + `StockDeductionRequest` ganan `StockCountSessionId` (int?, nullable; índice en movimientos). Migración idempotente + Designer + Snapshot.
- **S2 (Ciclo de vida y API)**: `/api/stock-counts`: `POST` crear [Admin/Manager] (201; scope por categoría), `GET` listado [Admin/Manager/Cashier], `GET {id}` detalle CIEGO, `POST {id}/scan {code, quantityDelta?=1}` (resuelve SKU/barcode; upsert +Δ; código desconocido → 404 claro; producto fuera de alcance → 409 claro), `PUT {id}/items/{productId} {countedQuantity}` (corregir), `DELETE {id}/items/{productId}` (quitar escaneo erróneo), `GET {id}/review` [Admin/Manager] (descuadre), `POST {id}/close` (congela teórico/costo por ítem), `POST {id}/apply` (aplica ajustes), `POST {id}/cancel`. Transiciones válidas: scan/edición solo en `Open`; close/cancel desde `Open` o `Closed`; apply solo desde `Closed`; terminales no admiten más. Security stamp + guards de rol.
- **S3 (Modo ciego)**: los DTOs de detalle/scan NUNCA exponen existencia teórica (solo producto + contado + timestamps). El descuadre vive únicamente en `/review` (Admin/Manager). El escáner resuelve por el endpoint de scan (ciego por construcción; sin `quick-check` para no filtrar datos).
- **S4 (Descuadre y aplicación)**: `/review` devuelve por ítem: contado, teórico (congelado al cerrar; si `Open`, teórico LIVE marcado como preview), Δ = contado − teórico, valor = Δ × costo; totales sobrantes/faltantes/neto (cantidad y USD). `apply`: pre-validación estricta (producto existente/no borrado/no adelanto/no grupo individual → si falla: 409 con detalle, sin tocar stock); ajustes en UN batch `UpdateStockBatchAsync` con `OriginType=Manual`, `ReasonCode=PhysicalCountCorrection`, `Observation="Toma física #C-{id} {Name}"`, `StockCountSessionId`, `AuthorizedByUserId` = aprobador; Δ = contado − stock actual al aplicar (la sesión deja el stock EXACTAMENTE en lo contado); ítems con Δ=0 se omiten; ítems NO escaneados NO se aplican (supuesto: conteo rotativo parcial — documentado); atomicidad: una transacción para estado `Applied` + movimientos con guard `xmin` (concurrencia → 409).
- **S5 (Web/móvil)**: nueva vista `stock-count` ("Conteo físico") en `App.jsx` + `navigation/roleViews.js` (Admin/Manager/Cashier; side-tests `Sidebar.test.js`/`roleViews.test.js` sincronizados) + item de Sidebar (grupo INVENTARIO). Página: lista de sesiones + crear (solo Admin/Manager), vista de conteo CIEGA con input de código + botón cámara reutilizando `BarcodeScannerModal` (resolver inyectable → scan endpoint), lista de ítems con +/− y edición de cantidad, y panel Admin (review con descuadre, Cerrar/Aplicar/Cancelar). Mobile-first (tokens/clases existentes). (supuesto: todo el flujo vive en Web; WPF no se toca — el roadmap ubica el escáner en Web y el Kardex WPF YA muestra los movimientos resultantes.)
- **S6 (Proceso)**: build 0/0, carriles + suite por partes, `npm test` + lint, verificación independiente, ANEXO 8.180, `docs/Ideas.txt` Paso 6 `[x]`, commits V0.15.
