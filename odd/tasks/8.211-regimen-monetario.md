# 8.211 — Régimen monetario configurable: moneda única/bimonetaria, códigos ISO y símbolos parametrizables

Objetivo: permitir que cada instalación configure un régimen monetario `Single` o `Dual`, con códigos ISO 4217 y símbolos de presentación parametrizables, sin reinterpretar ni recalcular el historial financiero. F1 entrega el contrato, la persistencia y la API del perfil; F2–F5 generalizan conversión, snapshots, clientes, comprobantes y guardas de transición.

Rama: `V0.15` · Entrega: work units locales; push/PR a decisión del mantenedor · Runner: `dotnet build CommandCenter.slnx -c Release` + `dotnet test`; web (cuando aplique): `npm test` / `npm run lint` / `npm run build`.

## Specs

S1 — Contrato del perfil monetario (F1). El perfil se compone de `Mode` (`Single` | `Dual`), `PrimaryCurrencyCode`, `PrimaryCurrencySymbol`, `SecondaryCurrencyCode?`, `SecondaryCurrencySymbol?` e `IsConfigured` de solo lectura. El código debe ser ISO 4217 alfa-3, normalizado a mayúsculas; el símbolo se recorta, admite 1–8 caracteres y no puede contener caracteres de control ni saltos de línea. En `Dual` la moneda secundaria es obligatoria y distinta de la principal; en `Single` no se acepta moneda secundaria. Defaults compatibles: `Dual`, `USD`/`$`, `VES`/`Bs.S`. `CurrencyFormat` sigue siendo una preferencia de separadores y NO forma parte del perfil.

S2 — Persistencia y atomicidad (F1). Las claves son `Monetary.Mode`, `Monetary.PrimaryCurrencyCode`, `Monetary.PrimaryCurrencySymbol`, `Monetary.SecondaryCurrencyCode` y `Monetary.SecondaryCurrencySymbol`. El guardado del perfil debe ser atómico (un solo `SaveChanges`) e invalidar la caché de cada clave. `IsConfigured=false` cuando la clave de modo falta o es ilegible; ante un perfil almacenado inválido se devuelven los defaults y `IsConfigured=false`. Sin migración de esquema.

S3 — API y RBAC (F1). `GET /api/settings/monetary-profile` disponible para `Admin` y `Manager`; `PUT /api/settings/monetary-profile` solo `Admin`, con el guard `CanMutateSettings`. Errores de validación → 400 con mensaje de dominio; falta de permiso → 403 sin persistir. F1 no emite SignalR ni modifica clientes.

S4 — Identidad de conversión y tasa por par (F2). En modo `Single`, convertir un monto a su misma moneda devuelve el monto exacto antes de cualquier redondeo y no invoca el anclaje BCV. En `Dual`, la tasa pertenece explícitamente a un par (`FromCode`/`ToCode`); USD/VES conserva BCV y los demás pares requieren una fuente confiable o carga manual definida. Un `ExchangeRate=1.0000` no sustituye la política de identidad.
  - Decisión F2 (mantenedor, 2026-10-26): los pares distintos de USD/VES se cargan **manualmente por un Admin, por día**. Persistencia: tabla `CurrencyPairRates` (`Id`, `RateDate` date, `FromCurrencyCode`/`ToCurrencyCode` ISO-3, `Rate` numeric(18,8), `UpdatedAtUtc`, `UpdatedByUserId`) con índice único `(RateDate, FromCurrencyCode, ToCurrencyCode)` y check `Rate > 0`. USD/VES y VES/USD se resuelven desde `ExchangeRateHistory` (BCV, techo 2dp, fallback al último registro ≤ fecha); los pares manuales se resuelven solo para la fecha exacta, sin fallback, y el inverso se deriva a 8dp. Fechas futuras y el par USD/VES se rechazan en la carga manual. Endpoints `GET/PUT /api/settings/manual-currency-rates`: GET Admin/Manager; PUT Admin + `CanMutateSettings`.

S5 — Precisión y redondeo por moneda (F2). La escala decimal de presentación, la escala de cálculo y la política de efectivo se resuelven por moneda; no se asume `2` decimales ni redondeo entero para todas. Las reglas históricas de USD/VES se preservan.
  - Decisión F2: `CurrencyPrecisionCatalog` usa las unidades menores ISO 4217 (0/2/3/4; default 2) y conserva la política histórica de efectivo VES = 0 decimales; para el resto, efectivo = unidad menor. `IMonetaryConversionService.ConvertAsync` devuelve el monto exacto cuando origen y destino son la misma moneda (sin consultar tasa ni redondear) y, en pares distintos, aplica la tasa del par y redondea a la escala de la moneda destino según `Digital`/`Cash`. F2 no cablea todavía checkout/caja/recibos; esa integración es F3.
  - Decisión 2A (mantenedor, 2026-10-27): al cablear VES cash en T3c se conserva el redondeo legacy de dos pasos (`PricingCalculator.RoundToCash`: 2dp→0dp); las monedas nuevas usan el redondeo de un paso a su unidad menor. No se unifica el comportamiento histórico de VES.
  - Decisión F3c1: `Bs.S`, `BsS` y `VES` son alias de la misma moneda ISO `VES` para precisión y conversión; los snapshots de presentación siguen usando `Bs.S` (compatibilidad UI/legacy). La identidad `Bs.S`↔`VES` debe devolver el monto exacto sin consultar tasa. T3c1 no cambia flujos, montos ni `PaymentMethodCurrencyResolver`.
  - Decisión F3c2 (opción A del mantenedor, 2026-10-27): esta iteración mantiene **primaria USD** y hace configurable la **secundaria** (VES/COP/MXN/EUR), pero el checkout solo se habilita para `Dual USD/VES` hasta T3c3. Se snapshotean `Sale.PrimaryAmount`, `Sale.SecondaryAmount`, `Sale.AppliedRateSource` y `SalePayment.OriginalAmount`; legacy se backfillea desde `TotalUSD`/`TotalBsS` y `CurrencyCode`. Cualquier perfil distinto de `Dual USD/VES` se rechaza al completar con un mensaje explícito; no se reinterpretan montos ni se crean ventas con otra moneda.
  - Decisión F3c3b1: en modo `Single`, la tasa efectiva es siempre `1` y el anclaje BCV se omite; la identidad se resuelve en `ExchangeRateAnchorService` con el perfil inyectado. Esta fase no habilita todavía ventas Single: la guarda de checkout sigue bloqueando el perfil hasta F3c3b2. No se expande aún `PaymentMethodCurrencyResolver`.
  - Decisión F3c3b3: al guardar el perfil en una instalación **sin datos financieros**, si el modo es `Single` 2dp se asegura un set canónico de métodos de pago en la moneda primaria: un efectivo y dos no-efectivo. Se reutilizan los métodos seed canónicos (`Efectivo`, `Tarjeta (Punto de Venta)`, `Transferencia / Pago Móvil`), se desactivan los duplicados legacy (`Cash`, `Card`, `Divisas (USD)`) solo si no tienen uso, y nunca se cambia la moneda de un método usado. La operación es idempotente, invalida la caché y notifica SignalR. En `Dual` no se toca el catálogo.
  - Decisión F3c3c (mantenedor, 2026-10-28): la primaria de `Dual` sigue siendo `USD` y la secundaria admitida para checkout es una moneda 2dp (`VES`, `COP`, `MXN`, `EUR`). `USD/VES` conserva BCV y la regla VES 2A; el resto usa la tasa manual diaria exacta (`CurrencyPairRates`) y **falla cerrado** si no existe. La fuente de tasa se snapshotea: `Bcv` para USD/VES, `Manual` para el resto, `Identity` en `Single`. Las reglas cash-friendly de producto (VES) solo se aplican cuando la secundaria es `VES`; las demás usan el techo 2dp. La moneda local de la gaveta es la primaria en `Single` y la secundaria en `Dual` (`VES` se presenta como `Bs.S`). El trabajo se divide en T3c3c1 (fundaciones, sin ampliar el guard) y T3c3c2 (habilitación integral).

S6 — Snapshots financieros y backfill (F3). Los agregados financieros guardan de forma aditiva los códigos de moneda, montos, par/tasa aplicada y snapshot de redondeo. Los registros legacy se backfillean como USD/VES sin recalcular montos ni tasas históricas.
  - Decisión F3a: cada `Sale` snapshotea `PrimaryCurrencyCode`, `SecondaryCurrencyCode` y `MonetaryMode` del perfil vigente al completarse. Legacy/instalaciones sin perfil: `USD`/`VES`/`Dual`. La venta en modo `Single` persiste secundaria `NULL`. Los montos, tasas y reglas de redondeo existentes NO cambian; el snapshot es aditivo y las columnas viejas siguen siendo la fuente de cálculo. La captura ocurre en el cierre regular y en el adelanto de efectivo (que crea una venta completada directa).
  - Decisión F3b3: cada `CashTransaction` snapshotea `CurrencyCode` de la moneda **física** de la gaveta. `SalePayment` Income, `CreditPayment` y `CreditRefund` usan la moneda persistida del método; apertura, cierre, vuelto, adelanto de efectivo, ajustes y cash-in/out usan la moneda local; caja chica y su reversa usan la moneda del gasto. El backfill legacy sigue la misma regla por `Source`/`Type`/`PettyCashExpenseId`/`PaymentMethodId`. No cambia montos, saldos ni la clasificación de arqueo.

S7 — Flujos backend (F3). Precios/costos, ventas y pedidos en espera, pagos, devoluciones, CxC, caja, adelantos, caja chica, cierres y facturas de proveedor respetan el perfil sin duplicar condicionales de modo en cada servicio.

S8 — Autoridad de la moneda del método de pago (F3). El backend valida y clasifica con la moneda persistida del método; el nombre solo es fallback legacy. Un rename no puede reclasificar movimientos históricos ni comprobantes.

S9 — Clientes Web/WPF (F4). Ambos clientes consumen el perfil activo, refrescan símbolos/modo sin reiniciar y mantienen el formato numérico separado. No se duplica matemática financiera en JavaScript.

S10 — Comprobantes y PDF (F4). Recibos y cierres muestran código ISO y símbolo configurado; los símbolos Unicode (`€`, `£`, `S/`) se renderizan correctamente o caen al código ISO, nunca a `?`. El cierre usa la moneda persistida, no una heurística por nombre.

S11 — Guardas de transición (F5). No se permite cambiar modo, moneda principal o par mientras exista una caja abierta o actividad financiera que quedaría reinterpretada; el cambio requiere un procedimiento explícito y nunca convierte saldos históricos en silencio.

S12 — Evidencia. RED→GREEN por task; `dotnet build CommandCenter.slnx -c Release` 0 errores/0 warnings; suite .NET completa; web `npm test`, `npm run lint`, `npm run build` cuando se toque Web; verificación independiente del work unit de riesgo alto; ANEXO XLIV (8.211) en `docs/reporte.txt`.
