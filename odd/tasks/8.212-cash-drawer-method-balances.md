# 8.212 - Existencias fisicas por metodo de pago

Rama: `V0.15`. Entrega: work units locales; push/PR a decision del mantenedor.
Runner: `dotnet build CommandCenter.slnx -c Release` + `dotnet test` + carril PostgreSQL.

## Specs

- S1. Cada metodo fisico (`IsCash == true && IsActive == true && IsDeleted == false`) valido
  para el regimen activo tiene una fila `CashDrawerSessionMethodBalance` por sesion, con
  `OpeningAmount`, `ClosingAmount`, `PaymentMethodName` y `CurrencyCode` snapshot.
- S2. `OpeningBalanceLocal`/`OpeningBalanceUsd` y `ClosingBalanceLocal`/`ClosingBalanceUsd`
  se mantienen como agregados de compatibilidad, sincronizados con las filas por metodo.
- S3. Si un flujo legacy no trae desglose por metodo y existe exactamente un metodo fisico
  para esa moneda, el fondo se auto-asigna; si hay mas de uno, se exige desglose explicito
  con HTTP 400 y mensaje claro.
- S4. El conjunto de metodos fisicos se congela al abrir la sesion. Un metodo desactivado
  con existencia sigue visible hasta el cierre; uno nuevo entra en la proxima sesion salvo
  apertura explicita.
- S5. El rollover de cierre arrastra el fondo/cierre por metodo a la nueva sesion, no solo
  los agregados local/USD.
- S6. `CurrentBalance` por metodo = apertura del metodo + entradas fisicas - salidas fisicas
  (ventas, vueltos, caja chica, reembolsos, cash-in/out y avances), usando el snapshot de
  moneda del movimiento.
- S7. Todos los roles que operan caja ven el saldo por metodo y la proyeccion del avance.
  El arqueo ciego de cierre mantiene la ocultacion de diferencias teoricas al Cashier.
- S8. `CashDrawerChanged(sessionId)` se publica post-commit, nunca dentro del lock.
