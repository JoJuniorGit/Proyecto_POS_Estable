# 8.186 — Paridad de redondeo Web: precio efectivo Bs.S en catálogo/buscador + USD efectivo en carrito/checkout + persistencia coherente

Objetivo: la versión web muestra el MISMO precio efectivo Bs.S que el POS local (política VesCashFriendly/UsdPsychological por artículo/global; Detal y Mayor) proyectado server-side con el motor único (`PricingRoundingPolicy`), sin duplicar matemática en JS; el Gran Total en USD del carrito/checkout web es el inverso del Total Bs.S efectivo (cero desfase de display) y las ventas web quedan contables equivalentes para Z/Paso 14 (EffectiveTotalUSD derivado de TotalBsS+AppliedRate persistidos — decisión ANEXO XII A3, sin migración).
Rama: V0.15 · Entrega: work units locales; push/PR a decisión del mantenedor · Runner: `dotnet build CommandCenter.slnx -c Release` + `dotnet test` por partes y secuenciales; web: `npm test` / `npm run lint` / `npm run build`.

## Specs

S1 — Proyección de redondeo en lectura (Catálogo y Buscador web). Mandato: "Los endpoints o servicios que alimentan el catálogo de la tienda web y la barra de búsqueda de productos deben inyectar el precio efectivo a través de PricingRoundingPolicyService o EffectivePriceVesHelper." / "El precio final mostrado al usuario en la interfaz web (tarjetas de producto, grilla de resultados de búsqueda) debe ser exactamente el mismo precio redondeado que muestra el POS local para ese canal (Detal/Mayor)."
  - Derivación: `ProductDto` y `ProductQuickInfoDto` ganan `EffectivePriceBsS` (Detal) y `EffectiveWholesalePriceBsS` (Mayor; 0 si no aplica). Se proyectan server-side con el kernel único `PricingRoundingPolicy.ProjectCashFriendlyBsS(usd, rate, rule, neverRoundDown)` (fallback canónico `ToBsSCeiling` para null/ExactMath/rate≤0 — misma semántica que `EffectivePriceVesHelper`), regla RESUELTA (`Product.RoundingRuleCashBs ?? DefaultVesRoundingRule`), toggle `EnforceMinimumMarginFloor` y tasa server-side `InventoryService.GetTodayExchangeRateAsync()` (cache `bcv_rate_today`). Una sola lectura de tasa/regla/toggle por request (no por ítem).
  - Superficies: listado paginado de catálogo (`InventoryService.CatalogQueries.cs`), sugerencias/búsqueda y quick-check (`CatalogQueries.cs` + `InventoryService.cs`), variantes usadas por web (`InventoryService.VariantQueries.cs` + `ProductsController.Variants.cs`). `MaskProductDto`/`MaskQuickInfoDto` copian los campos nuevos (lección 8.185 L7; masking de costo intacto, S6).
  - Invariante: NO se expone la política global al Cashier (`/api/settings/pricing-policies` sigue Admin/Manager); la proyección server-side evita ese cambio de auth. Campos canónicos existentes (`PriceBsS`, `PriceUSD`, reglas crudas) no cambian de semántica.
  - Refresco: al cambiar la tasa (SignalR `ExchangeRateChanged` ya vigente en web) el catálogo/búsqueda refetchean para re-proyectar (la proyección es del servidor). Mismo patrón que el re-search del POS WPF (8.143).

S2 — Cálculo del "USD Efectivo" en el Carrito Web. Mandato: "La lógica del carrito de compras de la versión web debe adoptar la misma matemática de ingeniería inversa implementada en el POS. Total USD Efectivo = Total Bs.S Redondeado / Tasa Activa." / "El Gran Total en $ mostrado al cliente web en la pantalla de Checkout o carrito debe ser este USD Efectivo, garantizando que Total $ * Tasa = Total Bs.S (cero desfase)."
  - Derivación backend: `CheckoutPreviewResponse` gana `EffectiveTotalUSD` = `round(TotalBsS/rate, 4, AwayFromZero)` con fallbacks canónicos (`TotalBsS<=0 || rate<=0` ⇒ `TotalUSD`), misma fórmula que `Sale.EffectiveTotalUSD` (ANEXO XII B1) en UN helper reutilizable (sin duplicar la inversa).
  - Derivación web: `CartContext` expone `effectiveTotalUSD` (preferencia: `currentSale.effectiveTotalUSD` del server; preview fresco cuando exista; fallback inverso `totalBsS/rateToUse`). `SummaryPanel` muestra el Gran Total $ EFECTIVO; `CheckoutModal` toma el valor del servidor (preview) en lugar de re-derivar. Display 2dp; 4dp contable. El `totalUSD` canónico se conserva para gates/contratos internos.
  - Identidad documentada (ANEXO XII): `$*rate == Bs.S` exacto es imposible con decimales finitos; se garantiza el inverso a 2dp de display y 4dp contable sobre el Bs.S efectivo (ancla).

S3 — Reutilización del motor Core (DRY). Mandato: "Se debe asegurar que la API o el Backend Web consuma exactamente los mismos helpers y registros de política (readonly record struct RoundingResult) optimizados en los tramos anteriores, sin duplicar la lógica matemática de redondeos quirúrgicos en una capa aislada para la web."
  - Derivación: prohibido portar Steps/piso/toggle a JS. Web = consumidor de valores proyectados por el backend; en las superficies alcanzadas se retira el cálculo canónico-lokal (`resolveBsSPrice`/`usdToBs`) reemplazándolo por los campos efectivos, dejando fallback canónico SOLO si el campo no viniera (compatibilidad documentada). La única matemática JS permitida es formateo y la inversa de display (`BsS/rate`), que no es la política.

S4 — Persistencia Web Coherente. Mandato: "Las órdenes o ventas generadas desde la versión web deben guardarse en la base de datos registrando el EffectiveUsdPrice como el monto real de la transacción, para mantener la coherencia en los reportes Z y el cálculo de ganancias del paso 14."
  - Derivación (decisión ANEXO XII A2/A3, vigente): el monto real transado ya queda persistido como `Sale.TotalBsS` (efectivo) + `AppliedRate` (snapshot inmutable); `Sale.EffectiveTotalUSD` se deriva a 4dp y se expone en `SaleDto` (mapeado). Z suma `SalePayments.AmountBsS` (efectivo) y no cambia; Paso 14 consumirá el DTO. **No se agrega columna física** (`EffectiveUsdPrice`): duplicaría un dato determinista (A2 diferida). Si el mantenedor exige columna física, es una decisión aparte (migración aditiva + backfill).
  - Deliverable: test de integración del flujo web por API (start → add items → preview → completa) que asegure persistencia efectiva, derivado 4dp y coherencia de totales (sin migración).

RED→GREEN por task; `dotnet build CommandCenter.slnx -c Release` 0/0; suites completas por partes/secuenciales (regla del mantenedor: un comando a la vez); web `npm test`, `npm run lint`, `npm run build` (bundle `Backend.API/wwwroot` regenerado, convención ANEXO XII B4); E2E WPF 50/50 como regresión; ANEXO XVII.

S6 — Invariantes. `TotalUSD` canónico y gates duales intactos; historial/recibos inmutables; masking de costo/margen intacto; cache de quick-info (15s/5min) y de tasa (`bcv_rate_today`) documentados; componentes muertos (`CheckoutHeader`/`CheckoutSummary`) fuera de alcance; sin cambios en `/api/settings` auth.
