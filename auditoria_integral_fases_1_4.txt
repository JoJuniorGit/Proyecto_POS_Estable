RESUMEN EJECUTIVO
--------------------------------------------------------------------------------
Se completó la auditoría estricta e implacable del repositorio CommandCenter POS,
abarcando Backend (.NET 10 / C#), Clientes Desktop (WPF / CommunityToolkit MVVM),
Frontend Web (React 19) y transporte en tiempo real (SignalR).

El análisis asumió el modelo de amenaza Zero-Trust donde el frontend está 
completamente comprometido, los hilos de red sufren latencia hostil y la concurrencia
alcanza picos transaccionales de saturación.

[SEC-01] [CRÍTICA - REMEDIADA CON RESIDUAL] Inyección de ajuste de redondeo arbitrario desde el payload
--------------------------------------------------------------------------------
- Archivo exacto: Sales.Module/Services/SalesService.Checkout.cs (Líneas 275-280)
- Archivo API: Backend.API/Controllers/SalesController.Checkout.cs (Líneas 100-110)
- Estado: REMEDIADO EN 8.149 (Server-authoritative recompute), con residual de deriva.
- Vector de ataque histórico:
  El payload POST /api/sales/{id}/complete enviaba `roundingAdjustment`. El backend

- Riesgo residual remanente:
  Existe una deriva de céntimos entre el TotalBsS calculado en CheckoutPreview
  (redondeo sobre TotalUSD * rate) y el TotalBsS persistido (suma de subtotales redondeados).

[SEC-07] [ALTA - ABIERTA] Conexiones WebSocket zombis en SignalR tras revocación de credenciales
--------------------------------------------------------------------------------
- Archivo exacto: Backend.API/Hubs/AuthorizationHub.cs (Líneas 16-100)
- Archivo exacto: Backend.API/Hubs/ExchangeRateHub.cs (Líneas 6-10)
- Archivo servicio: Backend.API/Services/SecurityStampValidator.cs (Líneas 99-115)
- Vector de ataque:
  La autenticación en SignalR se ejecuta únicamente durante el handshake HTTP de apertura
  del WebSocket. Cuando un administrador o cajero es despedido o revocado:
  1. `SecurityStampValidator.RevokeUserStampAsync` actualiza el sello en la BD.
  2. Sin embargo, jamás interactúa con `IHubContext` para abortar la conexión activa.
  3. No existe un `IHubFilter` que verifique el sello en cada método (`RequestAuthorization`, `ResolveAuthorization`).

  socket abierto puede continuar aprobando autorizaciones de precios o recibiendo eventos
  en tiempo real aunque su usuario esté formalmente revocado en base de datos.
- Corrección exigida:
  1. Inyectar `IHubContext<AuthorizationHub>` e `IHubContext<ExchangeRateHub>` en `SecurityStampValidator`:
       await _authHubContext.Clients.Group(AuthorizationHub.UserGroup(userId)).SendAsync("ForceDisconnect");
  2. Implementar un `IHubFilter` global que invoque `ValidateStampAsync` en cada llamada a método del Hub.

[PERF-01] [ALTA - ABIERTA] Bucle N+1 crítico en matching de facturas de proveedores
--------------------------------------------------------------------------------
- Archivo exacto: Inventory.Module/Services/SupplierInvoiceService.Staging.cs (Líneas 40-47)
- Archivo matching: Inventory.Module/Services/SupplierInvoiceService.Matching.cs (Líneas 37-117)
- Código vulnerable actual:

    {
        var unitCostUsd = ...;
        var match = await MatchProductAsync(supplier.Id, line, similarityThreshold, cancellationToken);
        invoice.Lines.Add(CreateStagedLine(line, match, unitCostUsd, request.OcrSourced));
    }
- Costo computacional del defecto:
  Por cada línea de la factura se disparan entre 1 y 4 consultas SQL independientes
  a PostgreSQL (búsqueda por SKU exacto, join con SupplierProductCodes y escaneo difuso).
  Para una factura de 150 ítems, esto representa más de 400 consultas individuales consecutivas,
  introduciendo entre 4.0 y 8.5 segundos de bloqueo en el connection pool y degradando la API.
- Refactorización para máxima velocidad:

    var barcodes = lines.Where(l => !string.IsNullOrWhiteSpace(l.Barcode)).Select(l => l.Barcode!).Distinct().ToList();
    var supplierCodes = lines.Where(l => !string.IsNullOrWhiteSpace(l.SupplierCode)).Select(l => l.SupplierCode!).Distinct().ToList();

    var productsByBarcode = await _context.Products.AsNoTracking()
        .Where(p => !p.IsDeleted && barcodes.Contains(p.SKU))
        .ToDictionaryAsync(p => p.SKU, cancellationToken);

    var productsBySupplierCode = await (
        from sc in _context.SupplierProductCodes.AsNoTracking()
        join p in _context.Products.AsNoTracking() on sc.ProductId equals p.Id
        where sc.SupplierId == supplier.Id && supplierCodes.Contains(sc.Code) && !p.IsDeleted
        select new { sc.Code, Product = p })
        .ToDictionaryAsync(x => x.Code, x => x.Product, cancellationToken);

    // Bucle en memoria puro (0 consultas SQL en la iteración principal):
    foreach (var line in lines)
    {
        ProductMatch? match = null;
        if (!string.IsNullOrWhiteSpace(line.Barcode) && productsByBarcode.TryGetValue(line.Barcode, out var pBarcode))
            match = new ProductMatch(pBarcode, MatchMethod.Barcode);
        else if (!string.IsNullOrWhiteSpace(line.SupplierCode) && productsBySupplierCode.TryGetValue(line.SupplierCode, out var pSupp))
            match = new ProductMatch(pSupp, MatchMethod.SupplierCode);
        else
            match = await FallbackFuzzyMatchAsync(supplier.Id, line, similarityThreshold, cancellationToken);

        invoice.Lines.Add(CreateStagedLine(line, match, unitCostUsd, request.OcrSourced));
    }

--------------------------------------------------------------------------------
- Archivo exacto: Desktop.Client/Views/ProductDialog.xaml.cs (Líneas 16-20)

[CLEAN-01] [MEDIA - ABIERTA] Más de 90 métodos zombis [NonAction] en controladores de API
--------------------------------------------------------------------------------
- Rutas afectadas:
  * Backend.API/Controllers/SalesController.Checkout.cs (Líneas 88, 173, 216)
  * Backend.API/Controllers/ProductsController.cs (Líneas 66, 92, 119, 147)
  * Backend.API/Controllers/CashDrawerController.cs (Líneas 62, 76, 123, 134, 330, 372)
  * Backend.API/Controllers/DailyClosureController.cs (Líneas 44, 65)
  * Backend.API/Controllers/UsersController.cs (Líneas 55, 66, 87)
- Principio violado: YAGNI (You Aren't Gonna Need It), Clean Code (Dead Code / Clutter).
- Diagnóstico arquitectónico:
  ASP.NET Core utiliza exclusivamente los métodos asíncronos sufijados con `*Async`
  para el despacho de peticiones HTTP. Los métodos síncronos decorados con `[NonAction]`
  son código muerto ("passthrough zombies") que duplican la superficie de mantenimiento,
  confunden a los desarrolladores y ensucian la arquitectura sin aportar valor en runtime.
- Reestructuración requerida:
  Erradicar todos los métodos `[NonAction]` de los controladores. Si los tests unitarios
  requieren invocar los controladores, deben llamar directamente a los métodos canónicos
  asíncronos pasando `CancellationToken.None`.

  Si el backend modifica la regla de tolerancia, los clientes divergirán de inmediato.
- Reestructuración requerida:
  Ambos clientes deben invocar exclusivamente `/api/sales/{id}/checkout-preview` y enlazar
  sus estados de botón ("Cobrar", "Saldo Restante") a las propiedades devueltas por el servidor.

[SRE-01] [CRÍTICA - REMEDIADA EN VENTAS, ABIERTA EN FACTURAS] Deadlocks por orden de bloqueo no determinista
--------------------------------------------------------------------------------
- Archivo remediado: Inventory.Module/Services/InventoryService.StockDeduction.cs (Línea 56)
- Archivo abierto: Inventory.Module/Services/SupplierInvoiceService.Apply.cs (Línea 82)
- Estado: REMEDIADO EN VENTAS (Change 8.149 con StockDeductionConsolidator).
- Diagnóstico del Edge Case:
  En el flujo de ventas, `StockDeductionConsolidator.ResolveAndConsolidate` ahora ordena
  ascendentemente por `ProductId`, garantizando que dos cajeros vendiendo los mismos productos
  adquieran los bloqueos de fila de PostgreSQL en el mismo orden (eliminando deadlocks AB-BA).
  SIN EMBARGO, en `SupplierInvoiceService.Apply.cs:82`:
    foreach (var line in invoice.Lines.OrderBy(candidate => candidate.Id))
  El ordenamiento es por `line.Id` (el ID de la línea de la factura), NO por `productId`.
  Si una factura de proveedor se aplica mientras se procesa otra factura con los mismos
  productos pero en orden inverso de líneas, se produce un deadlock en PostgreSQL (error 40P01).
- Solución arquitectónica concurrente:
  Ordenar deterministamente las líneas de la factura por `ResolvedProductId` antes de mutar:
    foreach (var line in invoice.Lines.OrderBy(candidate => candidate.ResolvedProductId))

[SRE-02] [CRÍTICA - PARCIALMENTE REMEDIADA] Idempotencia en endpoints transaccionales
--------------------------------------------------------------------------------
- Archivos remediados: POST /items, POST /transaction, POST /dailyclosure, POST /cancel.
- Archivo vulnerable ABIERTO: Backend.API/Controllers/SalesController.Checkout.cs (Línea 90)
- Estado actual:
  El filtro `[RequireIdempotencyKey]` fue desplegado con éxito en adición de ítems y cierres.
  SIN EMBARGO, `POST /api/sales/{id}/complete` (Línea 90) carece del atributo `[RequireIdempotencyKey]`.
- Diagnóstico del Edge Case:
  Si un cajero hace clic en "Finalizar Venta" y ocurre un microcorte de red antes de que
  el cliente reciba el HTTP 200, el cliente reintenta enviar la petición.
  Al no tener clave de idempotencia en `CompleteSaleAsync`:
  1. Si la primera petición ya completó la venta y la segunda llega milisegundos después,
     la segunda falla con HTTP 409 Conflict o ArgumentException ("La venta ya fue completada").
  2. El cliente asume error de cobro mientras que la venta fue registrada y la gaveta abierta,
     generando pánico en el operador y posible duplicación manual de cobros.
- Solución arquitectónica concurrente:
  Aplicar obligatoriamente `[RequireIdempotencyKey]` en `CompleteSaleAsync`:
    [HttpPost("complete")]
    [RequireIdempotencyKey]

[SRE-03] [ALTA - ABIERTA] Inanición del ThreadPool por AppLogger síncrono con lock global
--------------------------------------------------------------------------------
- Archivo exacto: Core/Logging/AppLogger.cs (Líneas 127-147)
- Archivo cliente: Core/Logging/ClientStateLogger.cs (Líneas 100-120)
- Código vulnerable actual:
    private static void WriteLog(string filePath, string level, string message)
    {
        lock (_lock) // BLOQUEO MUTEX GLOBAL
        {
            try
            {
                RotateLogFileIfNeeded(filePath);
                File.AppendAllText(filePath, formatted); // I/O SÍNCRONO A DISCO BLOQUEANTE
            }
            catch { }
        }
    }
- Diagnóstico del Edge Case y SRE:

[SRE-04] [CRÍTICA - ABIERTA] Ausencia de token de concurrencia xmin en entidad Product
--------------------------------------------------------------------------------
- Archivo exacto: Core/Entities/Product.cs (Líneas 16-97)
- DbContext: Inventory.Module/Data/InventoryDbContext.cs (Líneas 50-100)
- DbContext: Sales.Module/Data/SalesDbContext.cs
- Código vulnerable actual:
  En `Product.cs`, no existe ninguna propiedad `uint Version` mapeada a la columna de
  concurrencia de PostgreSQL `xmin`. En `OnModelCreating`, ninguna entidad llama a `.IsRowVersion()`.
- Diagnóstico del Edge Case:
  En `SupplierInvoiceService.Apply.cs` (Línea 186), el código intenta capturar:
    catch (DbUpdateConcurrencyException exception) when (attempt == 0 && ...)
  ESTE CATCH ES CÓDIGO MUERTO. Dado que EF Core no tiene configurado ningún token de
  concurrencia en `Product`, EF Core Npgsql NUNCA arroja `DbUpdateConcurrencyException` al actualizar
  un producto.
  Si un administrador edita el precio o costo de un producto en el catálogo simultáneamente
  con la aplicación de una factura de proveedor, ocurrirá un Lost Update silencioso: la última
  transacción que ejecute `SaveChanges` sobreescribirá ciegamente los cambios de la anterior sin alerta.
- Solución arquitectónica concurrente:
  1. Configurar el mapeo de `xmin` en el DbContext:
       modelBuilder.Entity<Product>()
           .Property<uint>("Version")
           .IsRowVersion();
  2. En PostgreSQL, esto mapea automáticamente el token a la columna de sistema `xmin`,
     haciendo que cualquier `UPDATE` verifique `WHERE xmin = @originalXmin` y active
     legítimamente `DbUpdateConcurrencyException` para que el bucle de reintento funcione.
