1. ARQUITECTURA Y STACK TECNOLOGICO
================================================================================

1.1 Vision general
--------------------------------------------------------------------------------
Sistema POS multiplataforma (Venezuela, doble moneda USD / Bs.S) compuesto por:

  Backend API   -> ASP.NET Core 10 (.NET 10.0.101, Kestrel). REST + SignalR.
                   Servicio Windows PosBackendService (NSSM). Es el unico
                   consumidor de PostgreSQL. Sirve tambien el build React
                   (wwwroot) estaticamente para la LAN.
  Web Frontend  -> React 19 + Vite 8 (cliente cajas/tablet, touch-first).
  Desktop       -> WPF .NET 10 (Desktop.Client) + Desktop.Client.Core (MVVM,
                   CommunityToolkit.Mvvm 8.4, MaterialDesignThemes 5.3).
  Core          -> Libreria compartida sin dependencias (entidades, DTOs,
                   interfaces, eventos MediatR, helpers, logging).
  Tests         -> CommandCenter.Tests (xUnit + Moq + coverlet + WebApplication
                   Factory). Suites Web aparte (node:test, 77/77).
  UpdaterService-> Auto-update del cliente WPF. Publicado pero NO integrado al
                   instalador (deuda activa 8.20-M08).
  Logistics     -> Modulo experimental NO productivo: DeliveryService con estado
                   efimero en ConcurrentDictionary (sin persistencia), aunque
                   sigue registrado en el DI de produccion (deuda 8.20-M08).

2. DOMINIO Y REGLAS DE NEGOCIO CRITICAS
================================================================================

2.1 Doble moneda y tasa BCV
--------------------------------------------------------------------------------
  * Los datos viajan como decimal (USD y Bs.S); la presentacion aplica 2
    formatos (Venezolano contable por defecto / Internacional) via formatters
    (web) y NumericCalculatorBehavior (WPF). La BD SIEMPRE guarda numeros.
  * Tasa: -> 1 registro/dia en ExchangeRateHistory. BcvScraperService scrapea
    el portal BCV (redondeo ceiling a 2 decimales via
    PricingCalculator.RoundExchangeRateCeiling - unico punto de redondeo).
  * Anclaje de venta: ante desvio > tolerancia, la venta ANCLA la tasa BCV del
    dia; desvio >= +-100% RECHAZA la venta. Unico fail-open restante (auditable
    y congelado por tests): tasa BCV INDISPONIBLE (0/error) -> se usa la tasa
    del cliente (continuidad de negocio).
  * Venta en espera: recalcualdo por KEYSET (WHERE Status=OnHold AND Id>
    lastId, batch 200) al cambiar la tasa (revision 8.19-H14).

2.2 Precios y redondeo (modelo financiero)
--------------------------------------------------------------------------------
  * Tax-Free Cost+Margin: precio USD de venta se deriva del costo + margen
    (sin impuestos; IVA no aplica/reservado de la logica de precio).
  * Redondeo: items/subtotales con 4 decimales (precision alta); totales y
    pagos con 2 decimales (RoundToDigital). UNIFICAR ESTO ROMPE LA INTEGRIDAD
    FINANCIERA (verificado no-bug en 8.16). Redondeo de precio hacia arriba
    (RoundPriceUp) centralizado en Core/Helpers/PricingCalculator.cs.
  * Zero-trust backend: el servidor recalcula/valida precios y redondeos
    aunque el cliente envie sus calculos (preview canonico).

2.3 Ventas, stock y consistencia
--------------------------------------------------------------------------------
  * Flujo CompleteSaleAsync: ExecutionStrategy -> transaccion compartida
    (SalesDbContext + InventoryDbContext en el mismo DbTransaction,
    ReadCommitted) -> deduccion sincrona de stock -> venta/pagos/caja/outbox/
    idempotencia -> commit atomico.
  * Idempotencia de venta: Idempotency-Key (regex) + SHA-256(Method+Path+Body);
    HIT=200 cacheado (X-Cache-Lookup), MISMATCH=422 + LogSecurityAudit.
  * Idempotencia de stock: dedupe POR SaleId (no por string Reason), campo
    StockMovement.SaleId (FASE 1 / 8.18-H03). CRITICO: la migracion que crea
    la columna no se aplica en produccion (8.20-C01).
  * Outbox: OutboxProcessorJob consume OutboxMessages con estado Dispatching
    + reclaim de stale >90s (FASE 1 / 8.18-H07), procesa con OrderBy+Take(20),
    purga Processed > 7d, dispatch at-least-once de eventos SignalR/MediatR.
  * Estados de venta: Pendiente, OnHold (en espera), Completada, Cacelada +
    DeliveryStatus para despacho. Ninguna modificacion a venta Finalizada.

2.4 Caja y corte
--------------------------------------------------------------------------------
  * Sesion de caja UNICA por usuario (indice single-open): apertura con fondo,
    movimientos Inflow/Outflow (fisico vs digital - IsPhysicalCash), cierre
    diario con tOtales por metodo de pago (ClosureDetails) + calculo de vuelto
    cruzados de divisa. Integridad monitoreada por pos-financial-integrity.
  * Adelanto de efectivo (ADV-001, IsCashAdvance): no deduce stock fisico.
  * BCV manual vs automatico: BcvExchangeRateJob auto-programado cada 2h
    contradice el diseno "BCV manual" declarado (deuda 8.16-B09/8.20-B10).

2.5 Seguridad y permisos
--------------------------------------------------------------------------------
  * JWT Bearer HMAC-SHA256 (JWT_SETTINGS_KEY), ClockSkew=0, roles
    Admin/Cashier/Driver/Manager; MustChangePassword para seeds (rotacion
    obligatoria en 8.9-B1). PasswordHasher PBKDF2.
  * RBAC por [Authorize] en cada endpoint; no hay X-User-Role confiable del
    cliente (el backend deriva el rol del token).
  * Quiebres de concurrencia: xmin como token nativo (8.2-A1); detalles de
    stock conmensurados con Numeric(18,3).

2.6 Reglas inviolables de integridad (los tests las congelan)
--------------------------------------------------------------------------------
  * Unificar productos/subtotales 4d y totales 2d rompe la integridad.
  * Ocultar mensajes de negocio (es. "Stock insuficiente") rompe UX y tests.
  * Prohibido formateadores de moneda ad-hoc fuera de formatters.js /
    NumericCalculatorBehavior.
  * Toda evolucion de esquema DEBE ser una migracion EF con atributo
    [Migration] (nunca ALTER TABLE inline en Program.cs Legacy Block).

3. INTEGRACION DE HARDWARE
================================================================================

3.1 Escaneres de codigo de barras
--------------------------------------------------------------------------------
  * CLIENTE WPF (cajas fijas): soporta pistolas USB/Bluetooth HID de tipo
    "keyboard wedge" (emulan teclado). Implementacion:
      - KeyboardWedgeScannerListener (Desktop.Client/Helpers/): listener global
        no intrusivo que discrimina rafagas de escaner (intervalo entre
        caracteres <= 60ms, configurable 20-150) vs tipeo humano; con guarda de
        foco (no intercepta cuando el cajero edita campos de texto
        interactivos). Se acopla/desacopla a la raiz de la vista.
      - PosViewModel.Scanning.cs: validacion con BarcodeValidator y semaforo
        compartido (_scannerLock) con la busqueda/sugerencia para evitar
        intercalaciones.
      - POS actualiza la linea del DataGrid al escanear; DataGrid_CellEditEnding
        commitea cantidad.
  * CLIENTE WEB (tablets): BarcodeScannerModal con @zxing/library (camara del
    dispositivo). Sin gating de permisos de camara adicional (API estandar).
  * Retroalimentacion auditiva/visual: ScannerFeedbackService (WPF) genera
    tonos PCM en memoria (880/440/220 Hz) identicos al web, sin bloquear UI.

3.2 Emparejamiento por QR (pairing)
--------------------------------------------------------------------------------
  * QrCodeHelper (Desktop.Client/Helpers/) genera el QR con ZXing
    BarcodeWriterPixelData. El QR codifica https://IP:5001/?paired=true; el
    reclamo single-use via ?pair= TOKEN efimero (backend /api/pairing/info) es
    DEFENSE-IN-DEPTH pendiente de reforzar en web (deuda 8.20-F20-05).

3.3 Despues del turno: entrada numerica ATM
--------------------------------------------------------------------------------
  * Teclados num. vendidos: AtmBehavior, NumericCalculatorBehavior (WPF) y
    useAtmKeypad/ATMInput (web) para montos con doble divisa. Son software
    (no perifericos).

3.4 PERIFERICOS NO INTEGRADOS (estado declarado al 2026-09-08)
