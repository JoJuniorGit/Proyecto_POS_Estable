1. RESUMEN EJECUTIVO Y MATRIZ DE ESTADO GLOBAL (REV. 7.0)
================================================================================
El sistema POS "CommandCenter" es una plataforma comercial distribuida de punto de
venta orientada a operaciones minoristas bajo entorno multimoneda (USD referencia /
Bs.S tasa oficial BCV): backend ASP.NET Core 10, cliente web React 19 / PWA,
cliente de escritorio WPF (.NET 10), servicio actualizador autónomo (UpdaterService)
y PostgreSQL 16 con arquitectura modular de doble contexto (SalesDbContext e InventoryDbContext).

Entre la Rev. 6.0 y la presente Rev. 7.0 (commit 77b9a7c) se culminó exitosamente
la ejecución y verificación del PLAN MAESTRO DE REMEDIACIÓN DEFINITIVA en 4 Fases:

[SEC-10 / ARQ-04] (NUEVO, ALTO) — Ausencia de ForwardedHeadersMiddleware y Bypass
Potencial de Verificación Loopback bajo Reverse Proxy
--------------------------------------------------------------------------------
- Clasificación: CWE-287 (Improper Authentication) / CWE-306 (Missing Authentication for Critical Function)
- Archivo y Línea: Backend.API/Controllers/PairingController.cs:28-36; Backend.API/Program.cs:219-244
- Diagnóstico:
  1. PairingController.cs permite acceso anónimo al endpoint GET /api/pairing/info
     si la petición proviene de loopback:
     remoteIp == null || IPAddress.IsLoopback(remoteIp) || remoteIp == "127.0.0.1" || remoteIp == "::1"
  2. Program.cs configura RateLimiter usando httpContext.Connection.RemoteIpAddress como partición.
  3. Ni Program.cs ni Startup configuran UseForwardedHeaders(new ForwardedHeadersOptions { ForwardedHeaders = ... }).
  4. Impacto: Si el sistema se publica detrás de un reverse proxy local (Nginx, IIS, YARP, Caddy o túnel Cloudflare),
     RemoteIpAddress será SIEMPRE 127.0.0.1. Como consecuencia:
     * CUALQUIER cliente externo de la red obtendrá acceso anónimo sin autenticación a /api/pairing/info.
     * Todas las solicitudes entrantes compartirán un único bucket de rate limiting, permitiendo que un solo
       cliente sature la cuota de todos los demás.
- Recomendación: Habilitar UseForwardedHeaders en Program.cs configurando KnownProxies o KnownNetworks
  autorizadas, o verificar explícitamente el encabezado X-Forwarded-For si proviene de proxies de confianza.

[ERR-04] (NUEVO, MEDIO) — Fuga de Excepciones Internas mediante ex.Message en Controladores
--------------------------------------------------------------------------------
- Clasificación: CWE-209 (Generation of Error Message Containing Sensitive Information)
- Archivo y Línea:
  * Backend.API/Controllers/DailyClosureController.cs:153-156
  * Backend.API/Controllers/ShiftsController.cs:177-180
  * Backend.API/Controllers/ExchangeRateController.cs:188-191
- Diagnóstico:
  En DailyClosureController y ShiftsController, el cierre de turno/sesión contiene:
    catch (Exception ex) { return BadRequest(new { Message = ex.Message }); }
  En ExchangeRateController:
    catch (Exception ex) { return StatusCode(500, new { Message = $"Error inesperado: {ex.Message}" }); }
  Estos bloques interceptan la excepción antes de que alcance el GlobalExceptionHandlerMiddleware,
  exponiendo nombres de tablas, columnas o cadenas internas de conexión al cliente HTTP y rompiendo
  el formato uniforme ProblemDetails RFC 7807.
- Recomendación: Eliminar los bloques catch (Exception ex) redundantes para que el middleware global
  capture la falla de forma segura, o registrar con AppLogger.LogCrash y retornar ProblemDetails estándar.

[UX-WEB-01 / ERR-05] (NUEVO, MEDIO) — Deserialización Incompleta de Errores RFC 7807 en api.js
--------------------------------------------------------------------------------
- Clasificación: CWE-703 (Improper Check or Handling of Exceptional Conditions)
- Archivo y Línea: Web.Frontend/src/services/api.js:215-236
- Diagnóstico:
  Al fallar una petición HTTP, api.js solo extrae errorMessage si existe jsonErr.message o jsonErr.Message.
  Si el backend responde con un ProblemDetails estándar de ASP.NET Core que contiene:
  * "detail": descripción del error RFC 7807
  * "errors": { "PropertyName": ["Mensaje de validación"] }
  api.js no extrae dichos campos y cae en el fallback:
  if (!errorBody.includes('<html') && errorBody.length < 300) errorMessage = errorBody;
  Esto provoca que el usuario final vea una cadena JSON cruda o "Error 400: Bad Request"
  en lugar de un mensaje comprensible.
- Recomendación: Expandir la extracción de errores en api.js para inspeccionar jsonErr.detail,
  jsonErr.title y Object.values(jsonErr.errors).flat().join('; ').

[PERF-06] (NUEVO, BAJO) — Consultas de Lectura Masiva sin AsNoTracking() en Servicios
--------------------------------------------------------------------------------
- Clasificación: CWE-400 (Uncontrolled Resource Consumption)
- Archivo y Línea:
  * Sales.Module/Services/CashDrawerService.cs:225-233 (GetHistoryAsync)
  * Backend.API/Controllers/SettingsController.cs:33-40 (GetExchangeRate)
- Diagnóstico:

[WPF-LEAK-01] (NUEVO, BAJO) — Fuga de Recursos y Handler 'async void' en ProductDialogViewModel
--------------------------------------------------------------------------------
- Clasificación: CWE-404 (Improper Resource Shutdown or Release) / CWE-703
- Archivo y Línea: Desktop.Client.Core/ViewModels/ProductDialogViewModel.cs:290-294, :674
- Diagnóstico:
  1. ProductDialogViewModel crea un _debounceTimer (DispatcherTimer) y suscribe un delegado async void:

[DOM-VAL-01] (NUEVO, BAJO) — Inconsistencia en Validación de SKU: Alfanumérico vs Numérico
--------------------------------------------------------------------------------

- Archivo y Línea:

  * Desktop.Client.Core/ViewModels/ProductDialogViewModel.cs:685

[SEC-11 / NET-01] (NUEVO, BAJO) — Restricción de Puertos en CORS Bloquea Despliegues Estándar (80/443)
--------------------------------------------------------------------------------
- Clasificación: CWE-346 (Origin Validation Error)
- Archivo y Línea: Backend.API/Program.cs:272-274
- Diagnóstico:
  La validación de subredes privadas RFC-1918 en la política de CORS contiene:
  bool isAllowedPort = port == 5000 || port == 5001 || port == 5173;
  Si un cliente despliega la aplicación web en un servidor estándar (puerto 80 HTTP o 443 HTTPS),
  o utiliza el comando 'vite preview' (puerto 4173), las peticiones preflight CORS son rechazadas
  automáticamente a menos que el origen se agregue manualmente en appsettings.Production.json.
- Recomendación: Documentar en la guía de despliegue que puertos no estándar requieren declaración
  explícita en Cors:AllowedOrigins, o admitir 80 y 443 en la lista de puertos permitidos por defecto.

4. ANÁLISIS DE ARQUITECTURA, FLUJO DE DATOS, RECURSOS Y RENDIMIENTO
================================================================================

1. ARQUITECTURA DEL BACKEND Y AISLAMIENTO DE CONTEXTOS:
   - Doble Contexto EF Core: InventoryDbContext y SalesDbContext operan sobre la misma base de datos
     PostgreSQL. La coordinación transaccional mediante rawDbTx.UseTransaction() implementada en
     SalesService.cs:388 garantiza atomicidad perfecta sin distributed transactions (2PC).
   - MediatR en Logística: Logistics.Module consume eventos de dominio en segundo plano
     (SaleDispatchedEvent, DeliveryAssignedEvent), eliminando dependencias circulares entre ventas
     y despacho de pedidos.

2. INTEGRIDAD FINANCIERA:
   - La aritmética multimoneda se encuentra centralizada en PricingCalculator.cs usando tipos
     decimal de C# con redondeo MidpointRounding.AwayFromZero para transacciones y RoundExchangeRateCeiling
     para la tasa BCV.
   - En la interfaz web (formatters.js), las operaciones se apoyan en toFixed de JavaScript. Aunque
     adecuado para formateo visual, se recomienda migrar cálculos internos a centavos enteros (integer cents)
     para evitar discrepancias de punto flotante IEEE-754.

3. RESILIENCIA Y MANEJO DE CONCURRENCIA:
   - Concurrencia Optimista: Las entidades principales utilizan tokens de concurrencia xmin de PostgreSQL.
   - Deducción de Stock por Lotes: UpdateStockBatchAsync resuelve de forma atómica y en una sola
     sentencia SaveChangesAsync la deducción completa de todos los productos de un ticket de venta,
     eliminando problemas N+1 de escritura.

4. GESTIÓN DE RECURSOS EN CLIENTE WPF:
   - BaseViewModel provee un ciclo de vida limpio con cancelación por token y desuscripción de
     WeakReferenceMessenger.
   - Virtualización de UI activa en DataGrid de inventario (VirtualizingStackPanel.IsVirtualizing="True",
     VirtualizationMode="Recycling", ScrollUnit="Pixel").

private void OnDebounceTimerTick(object? sender, EventArgs e)
{
    Core.Common.TaskExtensions.SafeFireAndForget(VerifySkuAsync(), "ProductDialogViewModel.VerifySku");
}

{

    _debounceTimer.Tick -= OnDebounceTimerTick;
