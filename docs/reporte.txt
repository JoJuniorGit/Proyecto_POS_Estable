1. RESUMEN EJECUTIVO Y MATRIZ DE ESTADO GLOBAL
================================================================================
El sistema POS "CommandCenter" es una solución cliente-servidor distribuida para
puntos de venta en entornos minoristas venezolanos. Opera con backend ASP.NET Core
8, frontend web React 19 / PWA para toma de pedidos móviles, cliente de escritorio
pesado en WPF (.NET 8) para cajas principales, servicio auxiliar de actualización
en segundo plano (UpdaterService) y base de datos relacional PostgreSQL con doble
DbContext (SalesDbContext e InventoryDbContext).

A lo largo de las revisiones previas se reconocieron avances sustanciales:
  - Implementación de control de concurrencia optimista con xmin (RowVersion).
  - Aritmética financiera estricta con tipos `decimal`, redondeo bancario y ceiling
    para tasas BCV.
  - Hashing PBKDF2 con sal por usuario (100.000 iteraciones SHA-256) sin texto plano.
  - Revocación en tiempo real por SecurityStamp con micro-caché y bypass inmediato
    en endpoints monetarios.
  - Bloqueo preventivo de cuentas (Lockout) tras 5 intentos fallidos por 15 minutos.
  - Almacenamiento seguro DPAPI para tokens en el cliente de escritorio.
  - Sembrado de secuencia de facturas en arranque (SELECT setval(...) GREATEST(MAX+1)).

No obstante, esta Auditoría Profunda (Rev. 4) revela que persisten brechas
estructurales críticas y se han identificado NUEVAS vulnerabilidades severas:

1. SEGURIDAD CRÍTICA (RCE): El servicio `UpdaterService` presenta una
   vulnerabilidad clásica de "Zip Slip" / Directory Traversal (CWE-22) en
   `Program.cs:52`. Al ejecutarse con privilegios SYSTEM o Administrador, un archivo
   ZIP malicioso puede sobreescribir cualquier binario del sistema operativo.
2. RENDIMIENTO CRÍTICO (RAM/GC): `CashDrawerService.GetCurrentBalanceLocalAsync`
   (línea 197) carga TODAS las transacciones de la sesión activa en memoria RAM
   haciendo `.Include(s => s.Transactions)` y suma en memoria con LINQ to Objects
   en lugar de delegar el cálculo a PostgreSQL con `SumAsync()`.
3. RENDIMIENTO DE CONSULTAS: Múltiples consultas en `SalesService.cs` combinan
   `.Include(s => s.Items)` y `.Include(s => s.Payments)` sin `.AsSplitQuery()`,
   generando una explosión cartesiana (Cartesian Product) en el motor relacional.
4. CONTROL DE ACCESO Y BYPASS DE LOCKOUT: El endpoint `POST /api/auth/change-password`
   es `[AllowAnonymous]`, no valida `LockoutEndUtc` ni incrementa `AccessFailedCount`.
   Un atacante puede utilizar este endpoint para realizar fuerza bruta ilimitada.
5. INTEGRIDAD FINANCIERA: `DailyClosureService` omite del arqueo diario las ventas
   cuyo método de pago haya sido desactivado durante el transcurso del día,
   generando descuadres contables silenciosos.
6. POLÍTICA DE CONTRASEÑAS DÉBIL: Longitud mínima de sólo 4 caracteres y asignación
   por defecto de la cédula del usuario (visible en facturas) como clave inicial.
7. CRASH LOGGER FALLIDO EN PRODUCCIÓN: El cliente WPF intenta escribir `crash.txt`
   en `Program Files`, donde los cajeros no tienen permisos, silenciando los errores
   en un `catch {}` vacío.

2. CONTRASTACIÓN EMPÍRICA Y VERIFICACIÓN DE HALLAZGOS PREVIOS
================================================================================
Se contrastó cada uno de los hallazgos registrados en la Rev. 3 contra el código
fuente real en el commit `bc88390`:

[C1] Clave de firma JWT por defecto en instalador y arranque:
  - Estado: 🟡 PARCIALMENTE MITIGADO.
  - Verificación: `Program.cs:139-148` y `TokenService.cs:22-36` abortan el
    arranque si la clave es vacía, menor a 32 caracteres, contiene el valor de
    desarrollo o la clave histórica `ddf95c83c01224202681eee4525087512ece338e47f4c4897b6c5d72459b8795`.
  - Brecha Remanente: En `installer/setup.iss:127`, la clave se genera con
    `Random(16)` de Inno Setup (un generador pseudoaleatorio no criptográfico
    predecible) y se almacena en texto plano en el registro de Windows
    (`HKLM\Software\POS\JwtSecretKey`, línea 130). Además, no existe ruta de
    migración automática para instalaciones existentes que abortan al actualizar.

[C2] Tráfico HTTP en texto claro en la red local (LAN):
  - Estado: ❌ VIGENTE.
  - Verificación: `Program.cs:41` configura Kestrel para escuchar en `0.0.0.0:5000`
    en HTTP sin cifrar. HTTPS en puerto 5001 es puramente opcional y requiere el

  - Brecha Remanente: La contraseña del PFX de desarrollo está hardcodeada en

[C3] Secretos versionados en el repositorio:
  - Estado: 🟡 PARCIALMENTE MITIGADO.
  - Verificación: `appsettings.Development.json` contiene contraseñas en claro
    (`Password=123456`, `AdminSeedPassword="Admin123!"`).
  - Brecha Remanente: `Configure-PosService.ps1:25` mantiene credenciales por
    defecto en su cabecera. La clave JWT se coloca en texto claro en los argumentos
    de servicio de NSSM (`AppEnvironmentExtra`).

[C4] Vulnerabilidad de tokens en cliente Web:
  - Estado: 🟡 PARCIALMENTE MITIGADO.
  - Verificación: Se implementó cookie `HttpOnly` y revocación en tiempo real por

[A1] Transacciones no atómicas entre Venta (Sales) e Inventario (Inventory):
  - Estado: ❌ VIGENTE.
  - Verificación: `SalesService.cs:553-561` invoca `_inventoryService.UpdateStockAsync`
    dentro de un bucle sobre los ítems de la venta con `allowNegativeStock: true`.
    Cada llamada a `UpdateStockAsync` ejecuta su propio `tx.CommitAsync()` en un
    `InventoryDbContext` independiente (`InventoryService.cs:770`). Si falla el
    guardado de la venta en `SalesDbContext` (`_context.SaveChangesAsync()`), el
    inventario ya quedó descontado en la base de datos sin reversión posible.

[A2] Numeración secuencial de facturas:
  - Estado: ✅ CORREGIDO.
  - Verificación: `Program.cs:441-442` siembra la secuencia de PostgreSQL al inicio:
    `SELECT setval('factura_number_seq', GREATEST((SELECT MAX("InvoiceNumber") FROM "Sales"), 0) + 1, false);`.
    Resta únicamente consolidar un índice único a nivel de esquema en `InvoiceNumber`.

[A3] Idempotencia en cobros concurrentes:
  - Estado: 🟡 PARCIALMENTE MITIGADO.
  - Verificación: El cliente Desktop genera y envía la cabecera `Idempotency-Key`
    (`CheckoutViewModel.cs`). Sin embargo, el backend la recibe en `SalesController.cs:295`
    y la graba únicamente en el payload del Outbox (`SalesService.cs:573`), sin
    validarla contra una tabla de claves de idempotencia en la base de datos para
    bloquear solicitudes POST concurrentes repetidas.

[A4] Borrado físico en lugar de archivado en `StockMovementArchiverJob`:
  - Estado: ❌ VIGENTE.
  - Verificación: `StockMovementArchiverJob.cs:55-67` ejecuta sentencias de eliminación
    directa (`DELETE FROM "StockMovements" WHERE "MovementDate" < ...`) purgando

[A5] Enumeración de usuarios y política de autenticación:
  - Estado: 🟡 PARCIALMENTE MITIGADO.
  - Verificación: Se añadió bloqueo de cuentas (Lockout) en `AuthController.cs:58-99`.
  - Brecha Remanente: `AuthController.cs:45` devuelve 404 ("Usuario no encontrado")

[A6] Políticas de seguridad en contraseñas:
  - Estado: ❌ VIGENTE.
  - Verificación: `UsersController.cs:96,166` permite contraseñas de apenas 4
    caracteres. Si se crea un usuario sin clave, se le asigna su cédula por defecto

[A7] Migraciones DDL crudas en arranque:
  - Estado: 🟡 PARCIALMENTE MITIGADO.
  - Verificación: Existen migraciones formales de EF Core (`Database.Migrate()`),

[A8] Reactivación incondicional de administradores en arranque:
  - Estado: ❌ VIGENTE.
  - Verificación: `Program.cs:644-670` busca a todos los usuarios con rol Admin y

SEC-01 (CRÍTICO) — Vulnerabilidad Zip Slip / Path Traversal en UpdaterService
--------------------------------------------------------------------------------
- Clasificación: CWE-22 (Improper Limitation of a Pathname to a Restricted Directory)
- Archivo y Línea: `UpdaterService/Program.cs:52-62`
- Impacto: Ejecución Remota de Código (RCE) / Sobrescritura Arbitraria de Archivos.
- Descripción:
  El servicio `UpdaterService` se ejecuta en segundo plano como servicio de Windows
  (frecuentemente bajo la cuenta `LocalSystem` o cuenta administrativa local). En
  el proceso de extracción del paquete de actualización:
  ```csharp
  // UpdaterService/Program.cs:52
  string destinationPath = Path.Combine(targetDir, entry.FullName);
  string? destDir = Path.GetDirectoryName(destinationPath);
  if (destDir != null && !Directory.Exists(destDir)) { Directory.CreateDirectory(destDir); }
  entry.ExtractToFile(destinationPath, overwrite: true);
  ```
  `Path.Combine` en .NET no previene secuencias de escape de directorio (`../` o
  `..\`). Si un archivo ZIP contiene una entrada como `../../../../Windows/System32/evil.dll`
  o sobreescribe binarios de inicio, `entry.FullName` se escapará de `targetDir` y
  escribirá en cualquier ubicación del disco con permisos de SYSTEM.
- Recomendación:
  Validar canónicamente que `destinationPath` comience con `targetDir`:
  ```csharp
  string fullDestPath = Path.GetFullPath(Path.Combine(targetDir, entry.FullName));
  string fullTargetDir = Path.GetFullPath(targetDir);
  if (!fullDestPath.StartsWith(fullTargetDir, StringComparison.OrdinalIgnoreCase))
  {
      throw new SecurityException($"Intento de Zip Slip detectado en entrada: {entry.FullName}");
  }
  ```

SEC-02 (CRÍTICO) — Generador PRNG Débil y Clave JWT en Texto Plano en Registro
--------------------------------------------------------------------------------
- Clasificación: CWE-338 (Use of Cryptographically Weak PRNG) / CWE-312 (Cleartext Storage)
- Archivo y Línea: `installer/setup.iss:123-131`
- Impacto: Falsificación de Tokens de Autenticación / Acceso Total Administrativo.
- Descripción:
  Cuando el instalador genera la clave de firma JWT, utiliza el algoritmo `Random()`
  de Pascal Script:
  ```pascal
  // setup.iss:126-127
  for I := 1 to 64 do
    Result := Result + HexChars[Random(16) + 1];
  ```
  `Random()` es un generador pseudoaleatorio predecible basado en el reloj del sistema.
  Cualquier atacante que conozca la fecha y hora aproximada de instalación puede
  reconstruir la semilla, derivar la clave JWT y forjar tokens de Administrador.
  Adicionalmente, en la línea 130 la clave se graba sin cifrar:
  `RegWriteStringValue(HKEY_LOCAL_MACHINE, 'Software\POS', 'JwtSecretKey', Result);`
  Cualquier usuario sin privilegios que ejecute `reg query HKLM\Software\POS` en la
  máquina puede leer la clave de firma del servidor.
- Recomendación:
  Delegar la generación exclusivamente a `System.Security.Cryptography.RandomNumberGenerator`
  en PowerShell / .NET y almacenar el secreto protegido mediante DPAPI o con ACLs
  estrictas legibles únicamente por `NT AUTHORITY\SYSTEM`.

SEC-03 (ALTO) — Bypass de Bloqueo de Cuenta (Lockout) en Cambio de Contraseña
--------------------------------------------------------------------------------
- Clasificación: CWE-307 (Improper Restriction of Excessive Authentication Attempts)
- Archivo y Línea: `Backend.API/Controllers/AuthController.cs:184-222`
- Impacto: Ataque de Fuerza Bruta Ilimitado contra Contraseñas de Usuarios.
- Descripción:
  El endpoint `POST /api/auth/change-password` está decorado con `[AllowAnonymous]`.
  Cuando un usuario envía su cédula y contraseña actual:
  1. Si la contraseña actual es errónea, la línea 211 retorna `Unauthorized("La contraseña actual es incorrecta")`.
  2. NO se consulta `user.LockoutEndUtc` para verificar si la cuenta está bloqueada.
  3. NO se incrementa `user.AccessFailedCount` ante el fallo.
  Un atacante puede utilizar este endpoint para lanzar miles de intentos de adivinación
  de contraseña sin ser bloqueado por el mecanismo de lockout de 5 intentos que sólo
  opera en `/api/auth/login`.
- Recomendación:
  Incorporar el control de intentos fallidos y validación de `LockoutEndUtc` dentro
  de `ChangePassword`, o exigir que este endpoint requiera autorización previa `[Authorize]`
  mediante un token temporal con claim específico `purpose: reset_password`.

SEC-04 (ALTO) — Políticas Inseguras de Contraseña y Cédula como Contraseña Inicial
--------------------------------------------------------------------------------
- Clasificación: CWE-521 (Weak Password Requirements)
- Archivo y Línea: `Backend.API/Controllers/UsersController.cs:96-107, 166-169`
- Impacto: Compromiso de Cuentas por Contraseñas Triviales y Predecibles.
- Descripción:
  1. La validación de contraseñas personalizadas admite claves de tan sólo 4 caracteres:
     `if (trimmedPass.Length < 4) return BadRequest(...)`.
  2. Cuando se crea un usuario sin especificar contraseña, el sistema asigna
     automáticamente el número de cédula como contraseña:
     `rawPassword = usernameClean; // UsersController.cs:105`
  En un entorno comercial, la cédula del cajero está impresa en todos los tickets
  de venta y comprobantes de caja. Esto permite que cualquier cliente o empleado
  ingrese al sistema con el usuario y la clave del cajero.
- Recomendación:
  Establecer longitud mínima de 8 caracteres con entropía alfanumérica y generar
  un PIN/clave temporal aleatorio de un solo uso que obligue al cambio en el primer
  inicio de sesión sin utilizar la cédula como secreto.

SEC-05 (ALTO) — Reactivación Automática de Administradores en Cada Arranque
--------------------------------------------------------------------------------
- Clasificación: CWE-284 (Improper Access Control)
- Archivo y Línea: `Backend.API/Program.cs:644-670`
- Impacto: Resurrección no Autorizada de Cuentas Administrativas Revocadas.
- Descripción:
  Durante el arranque del servidor, el código ejecuta:
  ```csharp
  var allAdmins = _salesDb.Users.Where(u => u.Role == Core.Entities.UserRole.Admin).ToList();
  foreach (var admin in allAdmins)
  {
      if (!admin.IsActive)
      {
          admin.IsActive = true;
          AppLogger.LogStart($"[Seed] Reactivated Admin user: {admin.Username}");
      }
      ...
  }
  ```
  Si un administrador fue despedido o comprometido y la gerencia desactiva su cuenta
  (`IsActive = false`), el siguiente reinicio del servidor (por actualización,
  corte de luz o mantenimiento) reactiva automáticamente la cuenta sin intervención.
- Recomendación:
  Eliminar la reactivación automática de todos los administradores. Si se requiere
  garantizar acceso de contingencia, verificar únicamente la existencia de un usuario
  `Root` o el administrador sembrado en la instalación, alertando al operador en caso
  de bloqueo sin forzar la activación masiva de cuentas desactivadas.

SEC-06 (ALTO) — Allowlist de Emparejamiento Web Permisiva hacia Redes Privadas
--------------------------------------------------------------------------------
- Clasificación: CWE-346 (Origin Validation Error) / Phishing en Red Local
- Archivo y Línea: `Web.Frontend/src/services/api.js:25-45`
- Impacto: Redirección de Sesión y Robo de Credenciales vía Códigos QR Maliciosos.
- Descripción:

  usuario al servidor del atacante.
- Recomendación:
  El cliente web solo debe conectarse a su host de origen o validar el emparejamiento
  mediante un token criptográfico efímero firmado por el backend legítimo.

PERF-01 (CRÍTICO) — Carga Masiva en Memoria y Suma del Lado del Cliente en Caja
--------------------------------------------------------------------------------
- Archivo y Línea: `Sales.Module/Services/CashDrawerService.cs:195-212`
- Diagnóstico:
  En el método `GetCurrentBalanceLocalAsync(int sessionId)`:
  ```csharp
  var session = await _context.CashDrawerSessions
      .Include(s => s.Transactions)
      .FirstOrDefaultAsync(s => s.Id == sessionId);

  if (session == null) return 0;

  var physicalIncomes = session.Transactions
      .Where(t => t.Source != CashTransactionSource.Opening && t.Type == CashTransactionType.Income && t.IsPhysicalCash)
      .Sum(t => t.AmountLocal);

  var physicalExpenses = session.Transactions
      .Where(t => t.Type == CashTransactionType.Expense && t.IsPhysicalCash)
      .Sum(t => t.AmountLocal);
  ```
- Impacto Técnico:
  1. `.Include(s => s.Transactions)` carga la colección COMPLETA de transacciones
     asociadas a la sesión activa en la memoria del proceso (RAM).
  2. Todas las entidades son registradas en el `ChangeTracker` del `DbContext`.
  3. En un turno con 500 a 2.000 ventas en efectivo y movimientos de caja, cada
     consulta de balance (que se ejecuta frecuentemente antes de cada egreso o
     adelanto) materializa miles de objetos, saturando el Garbage Collector (GC)
     y degradando la latencia de respuesta.
- Solución Recomendada:
  Ejecutar la agregación directamente en el motor PostgreSQL mediante consultas
  proyectadas con `SumAsync()` sin incluir la colección en memoria:
  ```csharp
  var openingBalance = await _context.CashDrawerSessions
      .Where(s => s.Id == sessionId)
      .Select(s => s.OpeningBalanceLocal)
      .FirstOrDefaultAsync();

  var netTransactions = await _context.CashTransactions
      .Where(t => t.SessionId == sessionId && t.IsPhysicalCash)
      .SumAsync(t => t.Type == CashTransactionType.Income && t.Source != CashTransactionSource.Opening
          ? t.AmountLocal
          : (t.Type == CashTransactionType.Expense ? -t.AmountLocal : 0));

  return openingBalance + netTransactions;
  ```

PERF-02 (ALTO) — Explosión Cartesiana en Consultas de Ventas sin Split Query
--------------------------------------------------------------------------------
- Archivo y Línea:
  - `Sales.Module/Services/SalesService.cs:121-125` (`GetSaleEntityAsync`)
  - `Sales.Module/Services/SalesService.cs:616-620` (`ConfirmPickupAsync`)
  - `Sales.Module/Services/SalesService.cs:1460-1465` (`UpdatePriceListAsync`)
- Diagnóstico:
  En varios métodos críticos se combinan múltiples colecciones 1:N sin `.AsSplitQuery()`:
  ```csharp
  var query = _context.Sales
      .Include(s => s.Items)
      .Include(s => s.Customer)
      .Include(s => s.Payments)
          .ThenInclude(p => p.PaymentMethod);
  ```
- Impacto Técnico:
  Cuando EF Core ejecuta un JOIN relacional entre `Sales`, `SaleItems` y `SalePayments`
  en una sola consulta SQL, el conjunto de resultados multiplica las filas devueltas
  ($N_{items} \times N_{payments}$). Para una venta con 30 ítems y 3 pagos parciales,
  se transmiten 90 filas completas con datos redundantes de la cabecera de venta.
- Solución Recomendada:
  Incorporar `.AsSplitQuery()` en todas las consultas de venta que incluyan tanto
  `Items` como `Payments`, o utilizar `.AsNoTracking()` con DTOs proyectados.

PERF-03 (MEDIO) — Purga Directa sin Particionado en StockMovementArchiverJob
--------------------------------------------------------------------------------
- Archivo y Línea: `Backend.API/Jobs/StockMovementArchiverJob.cs:55-67`
- Diagnóstico:
  El job elimina registros antiguos directamente con `ExecuteDeleteAsync()` sobre
  la tabla `StockMovements`. En bases de datos PostgreSQL de alto volumen, el borrado
  masivo genera sobrecarga en el Transaction Log (WAL), fragmentación de índices y

ARQ-01 (ALTO) — Discrepancia Financiera en Cierre Diario por Métodos Desactivados
--------------------------------------------------------------------------------
- Archivo y Línea: `Sales.Module/Services/DailyClosureService.cs:60-70`
- Diagnóstico:
  En el cálculo de los montos esperados por método de pago:
  ```csharp
  // DailyClosureService.cs:60-70
  var result = new List<ExpectedTotalDto>();
  foreach (var method in activeMethods)
  {
      salesTotals.TryGetValue(method.Id, out decimal expected);
      result.Add(new ExpectedTotalDto { ... });
  }
  ```
  La consulta previa `salesTotals` agrupa los pagos del día por `PaymentMethodId`.
  Sin embargo, el bucle sólo recorre `activeMethods` (`p.IsActive == true`).
  Si durante el día se cobraron ventas con un método que posteriormente fue
  desactivado por el administrador (por ejemplo, una cuenta bancaria deshabilitada
  a mitad de tarde), ese dinero recaudado se omite completamente del reporte de
  arqueo de caja, generando un descuadre contable no reconciliado.
- Solución Recomendada:
  Incluir todos los métodos activos MÁS cualquier método inactivo que tenga
  movimientos registrados en `salesTotals`:
  ```csharp
  var relevantMethodIds = activeMethods.Select(m => m.Id).Union(salesTotals.Keys);
  ```

ARQ-02 (ALTO) — Pérdida Silenciosa de Stock por Falta de Transacción Distribuida
--------------------------------------------------------------------------------
- Archivo y Línea: `Sales.Module/Services/SalesService.cs:553-591`
- Diagnóstico:
  La arquitectura utiliza dos `DbContext` independientes: `SalesDbContext` e
  `InventoryDbContext`.
  1. En `SalesService.CompleteSaleAsync`, se inicia una transacción en `SalesDbContext`.
  2. En el bucle de ítems, se llama a `_inventoryService.UpdateStockAsync`.
  3. Cada llamada a `UpdateStockAsync` confirma su propia transacción independiente
     en `InventoryDbContext` (`await tx.CommitAsync();` en `InventoryService.cs:770`).
  4. Si ocurre un fallo en la línea 590 al ejecutar `_context.SaveChangesAsync()` en
     `SalesDbContext` (por error de red, concurrencia o violación de clave única),
     la transacción de venta se revierte (`_transaction.RollbackAsync()`).
  5. Consecuencia: Las deducciones de stock de los ítems ya quedaron confirmadas
     en la base de datos. Los productos desaparecen del inventario contable sin que
     exista ninguna venta registrada.
- Solución Recomendada:
  - Compartir la misma conexión y transacción de base de datos entre ambos DbContext
    (`_inventoryDb.Database.UseTransaction(_salesDb.Database.CurrentTransaction.GetDbTransaction())`),
    o unificar las entidades en un único contexto relacional de base de datos.

ARQ-03 (MEDIO) — Emisión de Cabeceras Redundantes en Cliente Desktop por HTTP
--------------------------------------------------------------------------------
- Archivo y Línea: `Desktop.Client.Core/Services/UserSessionHeaderHandler.cs:54-59`
- Diagnóstico:
  El cliente de escritorio inyecta manualmente en cada petición HTTP:
  ```csharp
  request.Headers.Add("X-User-Role", _userSession.CurrentUser.Role.ToString());
  request.Headers.Add("X-User-Id", _userSession.CurrentUser.Id.ToString());
  ```
  La identidad y roles del usuario ya viajan firmados criptográficamente dentro del
  token JWT en la cabecera `Authorization: Bearer <token>`.
  Emitir estas cabeceras en texto plano por HTTP LAN no aporta ninguna función,
  expone metadatos de usuario a observadores en la red y crea el riesgo de que
  futuros desarrollos confíen en cabeceras manipulables en lugar de los claims del JWT.
- Solución Recomendada:
  Eliminar la inyección de `X-User-Role` y `X-User-Id` del `UserSessionHeaderHandler`.

  Permitir que las excepciones no controladas fluyan hacia el middleware global o
  utilizar el estándar RFC 7807 (`ProblemDetails`).

ERR-02 (MEDIO) — Fallo Silencioso del Crash Logger de WPF en Rutas de Instalación

// CÓDIGO PROBLEMÁTICO (CashDrawerService.cs:195-212):
public async Task<decimal> GetCurrentBalanceLocalAsync(int sessionId)
{
    var session = await _context.CashDrawerSessions
        .Include(s => s.Transactions) // CARGA MASIVA EN RAM
        .FirstOrDefaultAsync(s => s.Id == sessionId);

    if (session == null) return 0;

    var physicalIncomes = session.Transactions
        .Where(t => t.Source != CashTransactionSource.Opening && t.Type == CashTransactionType.Income && t.IsPhysicalCash)
        .Sum(t => t.AmountLocal);

    var physicalExpenses = session.Transactions
        .Where(t => t.Type == CashTransactionType.Expense && t.IsPhysicalCash)
        .Sum(t => t.AmountLocal);

    return session.OpeningBalanceLocal + physicalIncomes - physicalExpenses;
}

// CÓDIGO OPTIMIZADO RECOMENDADO (Cálculo directo en PostgreSQL):
public async Task<decimal> GetCurrentBalanceLocalAsync(int sessionId)
{
    var sessionOpening = await _context.CashDrawerSessions
        .Where(s => s.Id == sessionId)
        .Select(s => (decimal?)s.OpeningBalanceLocal)
        .FirstOrDefaultAsync();

    if (sessionOpening == null) return 0;

    var netTransactions = await _context.CashTransactions
        .Where(t => t.SessionId == sessionId && t.IsPhysicalCash)
        .SumAsync(t => 
            (t.Type == CashTransactionType.Income && t.Source != CashTransactionSource.Opening) 
                ? t.AmountLocal 
                : (t.Type == CashTransactionType.Expense ? -t.AmountLocal : 0m));

    return sessionOpening.Value + netTransactions;
}

{
    try
    {
