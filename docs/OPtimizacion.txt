Plan de Implementación: Pulido y Estabilización del Sistema POS
Objetivo General
Consolidar la confiabilidad, consistencia y usabilidad del sistema POS existente, corrigiendo fricciones operativas, cerrando brechas de errores y optimizando puntos críticos, sin introducir nuevas funcionalidades de negocio. El alcance abarca Backend API, Cliente Web (React) y Cliente de Escritorio (WPF).

Fases del Plan
Fase	Enfoque	Duración estimada
Fase 1	Auditoría y corrección de UX crítica	1 semana
Fase 2	Robustez de flujos financieros y manejo de errores	1 semana
Fase 3	Cobertura de pruebas automatizadas	1 semana
Fase 4	Seguridad y control de acceso	3-4 días
Fase 5	Consistencia visual y de componentes	3-4 días
Fase 6	Optimización focalizada de rendimiento	3 días
Fase 1: Auditoría y corrección de UX crítica
Objetivo: Identificar y resolver los puntos de fricción más comunes en la operación diaria.

Tareas específicas
Flujo de cobro (CheckoutModal)

Revisar estados del botón "Cobrar y Finalizar" en ventas normales, cuentas abiertas y mercancía en custodia.

Validar que los mensajes de error sean claros y accionables.

Asegurar que el teclado numérico ATM funcione en todos los campos monetarios.

Verificar que el cambio de cliente no borre los pagos ya ingresados.

Cierre de Caja (DailyClosure)

Revisar flujo en Web y WPF: acumuladores, guardado automático de comprobantes, reinicio de totales y preservación del historial.

Corregir cualquier inconsistencia entre el Cierre Z y la gaveta física.

Búsquedas y filtros

Unificar debounce y limpiado de query en todos los buscadores (clientes, productos, historial).

Asegurar que el dropdown flotante funcione correctamente en pantallas táctiles.

Navegación entre módulos

Revisar atajos de teclado (F1, F2, Escape) y la apertura de ventanas secundarias.

Garantizar que no queden ventanas huérfanas al cerrar la principal.

Criterios de aceptación:

El cajero puede completar una venta y un cierre de caja sin errores visibles ni pasos innecesarios.

Los buscadores responden de forma consistente y rápida.

No hay diálogos modales que bloqueen la operación sin razón.

Fase 2: Robustez de flujos financieros y manejo de errores
Objetivo: Blindar las operaciones que involucran dinero e inventario.

Tareas específicas
Transacciones de venta y abonos

Revisar CompleteSaleAsync, AddPaymentToHoldSaleAsync y CreateCreditInvoiceAsync para asegurar atomicidad y manejo de excepciones.

Validar que la limpieza de líneas en cero y las validaciones de totales funcionen correctamente.

Confirmar que no se descuente inventario dos veces en flujos con DeliverOnCredit.

Manejo de errores de red y base de datos

Probar escenarios de backend caído, timeout y reconexión.

Asegurar que el ResilienceHandler y el HealthPollingService se comporten de forma predecible.

Revisar logs de errores para detectar patrones recurrentes.

Persistencia de configuración

Validar que appsettings.Production.json, system.conf (si aplica) y client_settings.json no se sobrescriban en actualizaciones.

Comprobar que los cambios de IP/hostname se propaguen correctamente.

Criterios de aceptación:

Ninguna operación financiera queda a medias ante un fallo de red o de base de datos.

Los logs permiten diagnosticar cualquier incidencia sin exponer datos sensibles.

Fase 3: Cobertura de pruebas automatizadas
Objetivo: Aumentar la confianza en los cambios futuros.

Tareas específicas
Pruebas unitarias backend

Cubrir servicios críticos: SalesService, InventoryService, CashDrawerService, CustomerAdvanceService, PasswordHasher.

Añadir casos límite para cálculos de totales, redondeo, límites de crédito (si se mantienen), y estados de entrega.

Pruebas de integración

Implementar pruebas para flujos completos: creación de venta, abono, cierre de caja, edición de pedido.

Usar WebApplicationFactory o una base de datos de prueba (SQLite/InMemory) para validar la API.

Pruebas de UI (opcional)

Para Web, usar Cypress/Playwright en flujos críticos (login, agregar producto, cobrar).

Para WPF, implementar pruebas de ViewModel con mock de servicios.

Pruebas de regresión

Mantener la suite existente y ejecutarla en cada commit.

Definir un pipeline de CI que compile y corra las pruebas.

Criterios de aceptación:

Cobertura de código > 70% en servicios backend.

Las pruebas de integración cubren los 5 flujos más importantes.

Fase 4: Seguridad y control de acceso
Objetivo: Garantizar que solo usuarios autorizados realicen acciones sensibles.

Tareas específicas
Revisión de endpoints y roles

Verificar que todos los controladores tengan [Authorize] cuando corresponda.

Asegurar que los endpoints de administración (usuarios, configuración, cierre) exijan rol Admin o Manager.

Protección de datos sensibles

Confirmar que las contraseñas nunca se logueen ni se expongan en excepciones.

Revisar que los tokens JWT se almacenen de forma segura en WPF (memoria, no archivos planos).

Validación de entradas

Auditar DTOs y controladores para rechazar datos inválidos (valores negativos, longitudes, formatos de cédula/telefono).

Comprobar que la importación de productos valide correctamente todos los campos.

Criterios de aceptación:

Un cajero no puede acceder a funciones de administración.

Los intentos de acceso no autorizado se registran y rechazan.

Fase 5: Consistencia visual y de componentes
Objetivo: Homologar la experiencia entre Web y WPF, y reutilizar componentes.

Tareas específicas
Inventario de componentes duplicados

Identificar elementos comunes (paginación, buscador de clientes, diálogos de confirmación) y unificar su implementación o estilo.

Reemplazar MessageBox.Show por IDialogService en cualquier remanente.

Tema y estilos

Revisar que los colores, fuentes y espaciados sigan las variables del sistema (--bg-surface, --text-muted, etc.).

Ajustar botones y tarjetas para que sean consistentes en ambas plataformas.

Responsividad y accesibilidad

En Web, asegurar que los modales y tablas se vean bien en móvil.

En WPF, verificar que los controles se adapten a diferentes resoluciones y DPI.

Criterios de aceptación:

Un usuario que use ambas versiones no nota diferencias en la lógica ni en la apariencia.

No hay MessageBox nativos en el cliente WPF.

Fase 6: Optimización focalizada de rendimiento
Objetivo: Reducir tiempos de respuesta y consumo de recursos.

Tareas específicas
Revisar índices de base de datos

Crear índices faltantes en columnas de búsqueda y filtros (SKU, Name, CedulaOrRif).

Verificar que las consultas de listado usen AsNoTracking.

Monitorear N+1 queries residuales

Activar logs de EF Core y revisar flujos de venta y edición.

Corregir cualquier consulta que cargue datos innecesarios.

Caché de datos estáticos

Implementar caché para métodos de pago, clientes por defecto y tasas de cambio (si no está ya).

Invalidar caché de forma segura.

Criterios de aceptación:

El catálogo con 10.000 productos responde en < 500ms.

Las operaciones de venta completan en < 2s en un equipo estándar.

Métricas de Éxito
Métrica	Objetivo
Tiempo promedio de cobro	< 3 segundos
Errores críticos por semana	0
Cobertura de pruebas backend	> 70%
Tiempo de arranque backend	< 10 segundos
Satisfacción del cajero (encuesta informal)	> 90%
Plan de Ejecución
Semana 1: Fase 1 y 2 en paralelo, con pruebas manuales al final.

Semana 2: Fase 3 (pruebas automatizadas).

Semana 3: Fase 4 y 5.

Semana 4: Fase 6 y auditoría general.

Al final de cada fase, realizar una revisión con stakeholders y ajustar prioridades si es necesario.

✅ Conclusión
Este plan de pulido y estabilización permite consolidar el sistema POS existente antes de pensar en ampliaciones. Al enfocarse en la confiabilidad, experiencia de usuario y seguridad, se construye una base sólida que soportará futuras funcionalidades sin comprometer la operación diaria.
