Plan de Implementación: Pulido y Estabilización del Sistema POS
Objetivo General
Consolidar la confiabilidad, consistencia y usabilidad del sistema POS existente, corrigiendo fricciones operativas, cerrando brechas de errores y optimizando puntos críticos, sin introducir nuevas funcionalidades de negocio. El alcance abarca Backend API, Cliente Web (React) y Cliente de Escritorio (WPF).

Fases del Plan
Fase	Enfoque	Duración estimada
Fase 1	Auditoría y corrección de UX crítica	1 semana
Fase 2	Robustez de flujos financieros y manejo de errores	1 semana
Fase 3	Cobertura de pruebas automatizadas	1 semana
Fase 4	Seguridad y control de acceso	3-4 días
Fase 5	Consistencia visual y de componentes	3-4 días
Fase 6	Optimización focalizada de rendimiento	3 días
Fase 1: Auditoría y corrección de UX crítica
Objetivo: Identificar y resolver los puntos de fricción más comunes en la operación diaria.

Tareas específicas
Flujo de cobro (CheckoutModal)

Revisar estados del botón "Cobrar y Finalizar" en ventas normales, cuentas abiertas y mercancía en custodia.

Validar que los mensajes de error sean claros y accionables.

Asegurar que el teclado numérico ATM funcione en todos los campos monetarios.

Verificar que el cambio de cliente no borre los pagos ya ingresados.

Cierre de Caja (DailyClosure)

Revisar flujo en Web y WPF: acumuladores, guardado automático de comprobantes, reinicio de totales y preservación del historial.

Corregir cualquier inconsistencia entre el Cierre Z y la gaveta física.

Búsquedas y filtros

Unificar debounce y limpiado de query en todos los buscadores (clientes, productos, historial).

Asegurar que el dropdown flotante funcione correctamente en pantallas táctiles.

Navegación entre módulos

Revisar atajos de teclado (F1, F2, Escape) y la apertura de ventanas secundarias.

Garantizar que no queden ventanas huérfanas al cerrar la principal.

Criterios de aceptación:

El cajero puede completar una venta y un cierre de caja sin errores visibles ni pasos innecesarios.

Los buscadores responden de forma consistente y rápida.

No hay diálogos modales que bloqueen la operación sin razón.

Fase 2: Robustez de flujos financieros y manejo de errores
Objetivo: Blindar las operaciones que involucran dinero e inventario.

Tareas específicas
Transacciones de venta y abonos

Revisar CompleteSaleAsync, AddPaymentToHoldSaleAsync y CreateCreditInvoiceAsync para asegurar atomicidad y manejo de excepciones.

Validar que la limpieza de líneas en cero y las validaciones de totales funcionen correctamente.

Confirmar que no se descuente inventario dos veces en flujos con DeliverOnCredit.

Manejo de errores de red y base de datos

Probar escenarios de backend caído, timeout y reconexión.

Asegurar que el ResilienceHandler y el HealthPollingService se comporten de forma predecible.

Revisar logs de errores para detectar patrones recurrentes.

Persistencia de configuración

Validar que appsettings.Production.json, system.conf (si aplica) y client_settings.json no se sobrescriban en actualizaciones.

Comprobar que los cambios de IP/hostname se propaguen correctamente.

Criterios de aceptación:

Ninguna operación financiera queda a medias ante un fallo de red o de base de datos.

Los logs permiten diagnosticar cualquier incidencia sin exponer datos sensibles.

Fase 3: Cobertura de pruebas automatizadas
Objetivo: Aumentar la confianza en los cambios futuros.

Tareas específicas

Cubrir servicios críticos: SalesService, InventoryService, CashDrawerService, CustomerAdvanceService, PasswordHasher.

Añadir casos límite para cálculos de totales, redondeo, límites de crédito (si se mantienen), y estados de entrega.

Pruebas de regresión

Definir un pipeline de CI que compile y corra las pruebas.

Criterios de aceptación:

Cobertura de código > 70% en servicios backend.

Las pruebas de integración cubren los 5 flujos más importantes.

Responsividad y accesibilidad

En WPF, verificar que los controles se adapten a diferentes resoluciones y DPI.

Criterios de aceptación:

Un usuario que use ambas versiones no nota diferencias en la lógica ni en la apariencia.

No hay MessageBox nativos en el cliente WPF.

Fase 6: Optimización focalizada de rendimiento
Objetivo: Reducir tiempos de respuesta y consumo de recursos.

## 1. Transacciones de Venta y Abonos

### 1.1 Revisar `CompleteSaleAsync`

#### Contexto
`CompleteSaleAsync` es el método que finaliza una venta (normal o cuenta abierta), registra pagos, actualiza inventario y puede disparar eventos de cierre de caja.

#### Tareas detalladas

##### Paso 1: Auditoría de atomicidad
- Verificar que el método utilice una **única transacción de base de datos** (`BeginTransactionAsync`) para todas las operaciones:
  - Crear `Sale`/actualizar estado.
  - Añadir `SalePayment`.
  - Actualizar `Stock`/`ReservedQuantity`.
  - Registrar `CashTransaction` si el pago es en efectivo.

- Si no existe una transacción, implementarla:

```csharp
await using var transaction = await _context.Database.BeginTransactionAsync(cancellationToken);
try
{
    // 1. Validar totales
    // 2. Registrar pagos
    // 3. Descontar inventario
    // 4. Actualizar sesión de caja
    await _context.SaveChangesAsync(cancellationToken);
    await transaction.CommitAsync(cancellationToken);
}
catch (Exception ex)
{
    await transaction.RollbackAsync(cancellationToken);
    _logger.LogError(ex, "Error al completar venta {SaleId}", saleId);
    throw new InvalidOperationException("No se pudo completar la venta. Todos los cambios fueron revertidos.", ex);
}
```

##### Paso 2: Validación de totales y pagos
- Antes de guardar, verificar:
  - `sale.Payments.Sum(p => p.Amount) > 0` (ya implementado).
  - `RemainingBalanceUsd <= 0.05` para venta normal; para cuentas abiertas, permitir abonos parciales pero nunca superar el saldo.

- Añadir validación de sobrepago:

```csharp
if (TotalPaidUsd > TotalUsd + 0.05m)
    throw new InvalidOperationException("El monto pagado excede el total de la venta.");
```

##### Paso 3: Limpieza de líneas en cero
- Antes de persistir, eliminar `SalePayment` con `Amount <= 0` usando `Remove` (no reasignar la colección):

```csharp
var zeroPayments = _sale.Payments.Where(p => p.Amount <= 0).ToList();
foreach (var p in zeroPayments)
    _sale.Payments.Remove(p);
```

##### Paso 4: Manejo de excepciones
- Capturar `DbUpdateException`, `PostgresException` y `InvalidOperationException`.
- Si ocurre un fallo, **rollback completo** y lanzar una excepción controlada con mensaje descriptivo.

#### Criterios de aceptación
- [ ] Una venta completada persiste en una sola transacción: si falla cualquiera de los pasos, no se guarda nada.
- [ ] Los pagos con monto 0 no se almacenan.
- [ ] Sobrepagos se rechazan con mensaje claro.
- [ ] El inventario se descuenta exactamente una vez.

### 1.2 Revisar `AddPaymentToHoldSaleAsync`

#### Contexto
Método para registrar abonos parciales en cuentas abiertas sin cerrar la venta.

#### Tareas detalladas

##### Paso 1: Validación de estado
- Verificar que la venta esté en estado `OnHold` y no `Completed` ni `Cancelled`.
- Si la venta es de tipo anticipo (`IsAdvancePayment`), validar que el abono no exceda el saldo a favor.

##### Paso 2: Conversión de moneda
- Si el abono se hace en Bs.S, convertirlo a USD usando la tasa actual de la venta (`AppliedRate`) o la tasa BCV del día. Utilizar `Math.Round(..., 2, MidpointRounding.AwayFromZero)` solo para el monto final, no para conversiones intermedias.

##### Paso 3: Registro del pago
- Añadir un `SalePayment` con:
  - `SaleId`
  - `PaymentMethodId`
  - `Amount` (USD)
  - `AmountBsS` (si aplica)
  - `ExchangeRate` (tasa del momento)
  - `CreatedAt = DateTime.UtcNow`

##### Paso 4: Actualización del saldo
- Recalcular `TotalPaidUsd` y `RemainingBalanceUsd`.
- No cambiar el estado a `Completed` salvo que el saldo quede en 0 (opcional según regla de negocio).

##### Paso 5: Manejo de errores
- Si falla el guardado, revertir cualquier cambio y lanzar excepción con mensaje.
- Registrar `[TRANSACTION]` en logs con montos y usuario.

#### Criterios de aceptación
- [ ] Los abonos parciales quedan registrados y el saldo pendiente se actualiza correctamente.
- [ ] No se puede abonar más de lo adeudado.
- [ ] La venta permanece `OnHold` tras un abono parcial.
- [ ] Si el pago es en efectivo, se actualiza la sesión de caja.

### 1.3 Revisar `CreateCreditInvoiceAsync`

#### Contexto
Crea una factura entregada a crédito con descuento inmediato de inventario.

#### Tareas detalladas

##### Paso 1: Transacción compartida

## 1. Pruebas Unitarias Backend

### 1.1 Servicios Críticos a Cubrir

| Servicio | Métodos principales a probar | Casos límite |
|----------|------------------------------|--------------|
| **`SalesService`** | `CompleteSaleAsync`, `AddPaymentToHoldSaleAsync`, `CreateCreditInvoiceAsync`, `HoldSaleAsync`, `UpdateSaleItemsAsync`, `CancelSaleAsync` | Pagos exactos, sobrepagos, redondeo con `MidpointRounding`, cero pagos, estados de entrega (`Delivered`, `Undelivered`, `PendingPickup`). |
| **`InventoryService`** | `GetProductsPagedAsync`, `GetProductsByIdsAsync`, `UpdateStockAsync`, `ValidateAndAdjustQuantityForProductAsync` | Filtros, ordenamiento, paginación, productos fraccionados, stock insuficiente. |

### 1.2 Casos Límite Específicos

- **Cálculos de totales**:  
  - Venta con múltiples ítems y redondeo a dos decimales.  
  - Conversión USD ↔ Bs.S con tasa `AppliedRate` y `MidpointRounding.AwayFromZero`.  
  - Productos con precios calculados por costo + margen (techo fiscal).  

- **Redondeo**:  
  - Precio `1.20001` → `1.21` (ceil).  
  - Precio `1.20000` → `1.20` (exacto).  

- **Límites de crédito** (si aún se aplican):  
  - Pedido en espera que excede el límite → lanzar excepción (si la regla se mantiene).  
  - Abono que reduce la deuda por debajo del límite → éxito.  

- **Estados de entrega**:  
  - `HoldSaleAsync` sin `DeliverOnCredit` → `DeliveryStatus = Undelivered`.  
  - `CreateCreditInvoiceAsync` con entrega → `DeliveryStatus = Delivered` y descuento de inventario inmediato.  
  - `CompleteSaleAsync` en crédito entregado no debe volver a descontar.

# Fase 4: Seguridad y Control de Acceso — Plan de Implementación Detallado

## Objetivo  
Garantizar que solo usuarios autorizados realicen acciones sensibles, mediante la revisión sistemática de endpoints, roles, protección de datos sensibles y validación de entradas. El resultado será un sistema donde un Cajero no pueda acceder a funciones administrativas y donde cada intento no autorizado se registre y rechace.

## Alcance  
- **Backend API (ASP.NET Core)**: Controladores, middleware de autenticación JWT, servicios de usuario, DTOs y validaciones.  
- **Cliente Web (React)**: Gestión de roles en componentes, protección de rutas, manejo de tokens.  
- **Cliente Escritorio (WPF)**: Almacenamiento seguro de JWT, ocultamiento de funcionalidades según rol, `IDialogService` para errores de acceso.  
- **Base de Datos**: Índices, restricciones y migraciones si se requieren.

---

## 1. Revisión de Endpoints y Roles

### 1.1 Auditoría de Controladores

**Objetivo:** Verificar que todos los controladores que manejan operaciones sensibles tengan `[Authorize]` y, cuando corresponda, roles específicos.

**Tareas detalladas:**

1. **Inventario de controladores**  
   Listar todos los `Controller` del proyecto y sus acciones, con el método HTTP y el nivel de acceso actual.

2. **Clasificar por nivel de sensibilidad**:
   - **Público**: `Login`, `Health`, `Pairing Info` (con restricciones).  
   - **Cajero**: Operaciones de venta, cobro, cierre de caja (acciones propias del turno).  
   - **Admin/Manager**: Gestión de usuarios, clientes, catálogo, configuración, tasa de cambio, importación masiva.

3. **Aplicar atributos**:
   ```csharp
   [Authorize] // solo autenticado, sin rol específico
   public class SalesController : ControllerBase { ... }

   [Authorize(Roles = "Admin,Manager")]
   public class UsersController : ControllerBase { ... }
   ```

4. **Revisar endpoints de emparejamiento**:
   - `GET /api/pairing/info`: Debe permitir acceso localhost sin token y con token válido para dispositivos remotos.
   - `GET /api/health`: Libre, pero sin exponer datos sensibles.

5. **Agregar política de autorización global**  
   En `Program.cs`:
   ```csharp
   app.UseAuthentication();
   app.UseAuthorization();
   ```

6. **Probar acceso no autorizado**  
   - Usando Postman o tests de integración, verificar que:
     - Sin token → `401 Unauthorized`.
     - Token de Cajero en endpoint de Admin → `403 Forbidden`.
     - Token de Admin en endpoint de Cajero → éxito.

## 2. Protección de Datos Sensibles

### 2.1 Contraseñas

**Objetivo:** Garantizar que las contraseñas no se logueen ni se expongan en excepciones.

**Tareas:**

1. **Auditar todos los logs**  
   Buscar en `Console.WriteLine`, `_logger.LogInformation/Error/Warning` cualquier referencia a `Password`, `PasswordHash`, `Clave`, etc.  
   - Corregir para que solo se muestren IDs o nombres de usuario.

2. **Revisar `PasswordHasher`**  
   - Verificar que `HashPassword` y `VerifyPassword` nunca reciban o retornen contraseñas en texto plano en logs.
   - Si ocurre una excepción, el mensaje no debe incluir la contraseña ingresada.

3. **DTOs seguros**  
   - `LoginRequest` contiene `Password`; esto es inevitable, pero debe excluirse de serialización en respuestas.
   - Añadir `[JsonIgnore]` o usar `record` que no devuelva `Password`.

### 2.2 Tokens JWT

**Objetivo:** Asegurar que el token se almacene de forma segura en el cliente WPF y se maneje adecuadamente en Web.

**Tareas en WPF:**

1. **Almacenamiento en memoria**  
   - Actualmente `UserSession` guarda el token en una propiedad `string`.
   - Confirmar que **no** se persista en `client_settings.json` ni en `%LocalAppData%`.
   - Si existe código que lo escriba en disco, eliminarlo.

2. **Manejo de expiración**  
   - El `UserSessionHeaderHandler` ya intercepta `401` y llama `Logout()`.
   - Verificar que también limpia el token de la memoria al hacer logout.

3. **Registro de token**  
   - No se debe loguear el token JWT en ninguna circunstancia.

**Tareas en Web:**

1. **Almacenamiento en `localStorage`**  
   - El token se guarda en `localStorage` como `pos_token`.
   - Aceptable para esta fase, pero documentar que en producción se podría considerar `httpOnly cookies` (mejora futura).
   - Asegurarse de que no se envíe a logs ni a servicios externos.

2. **Refresh / Expiración**  
   - Si el token expira, el interceptor debe redirigir al login.

### 2.3 Auditoría de acceso

**Objetivo:** Registrar intentos de acceso no autorizado.

**Tareas:**

1. **Middleware de auditoría**

     - Timestamp

     - Ruta solicitada

   - Registrar en `logs/security-audit.log`.

# Fase 6: Optimización Focalizada de Rendimiento — Plan de Implementación Detallado

## Objetivo
Reducir los tiempos de respuesta y el consumo de recursos del sistema POS, centrándose en los puntos críticos identificados en el diagnóstico y las fases previas. ## Alcance
- **Backend API**: `InventoryService`, `SalesService`, `CashDrawerService`, `DailyClosureService` y contexto de EF Core.
- **Cliente Web (React)**: No se esperan cambios de rendimiento backend en esta fase, salvo que se detecten problemas en el frontend (debounce ya aplicado en Fase 1).
- **Cliente Escritorio (WPF)**: Virtualización y carga diferida ya cubiertas; esta fase se enfoca en backend y consultas.

## 1. Revisión y Creación de Índices en Base de Datos

### 1.1 Objetivo
Garantizar que las búsquedas y filtros principales utilicen índices B-Tree adecuados, evitando escaneos secuenciales en tablas grandes.

### 1.2 Índices a Crear o Verificar

| Tabla | Columna(s) | Tipo de índice | Justificación |
|-------|-----------|----------------|---------------|
| `Products` | `SKU` | B-Tree único | Búsqueda por código de barras en catálogo y POS. |
| `Products` | `Name` | B-Tree (no único) | Búsqueda por nombre y filtros de catálogo. |
| `Products` | `IsActive` | B-Tree parcial `WHERE IsActive = true` | Consultas de productos activos (sugerencias, listados). |
| `Customers` | `CedulaOrRif` | B-Tree único funcional `LOWER(CedulaOrRif)` | Búsqueda case-insensitive de clientes. |
| `Customers` | `Name` | B-Tree (no único) | Filtros por nombre en listas y selección. |
| `Sales` | `Status` | B-Tree parcial `WHERE Status = 1` (OnHold) o `Status = 2` (Completed) | Consultas de cuentas abiertas, historial. |
| `Sales` | `DeliveryStatus` | B-Tree | Filtrar retiros pendientes y consumos. |
| `Sales` | `InvoiceNumber` | B-Tree | Búsqueda por factura en historial. |
| `Sales` | `Date` | B-Tree | Consultas por rango de fechas en cierres y reportes. |
| `SaleItems` | `SaleId` | B-Tree (FK) | Cargar ítems de una venta rápidamente. |
| `SalePayments` | `SaleId` | B-Tree (FK) | Cargar pagos de una venta. |
| `CashTransactions` | `SessionId` | B-Tree | Transacciones de caja por sesión. |
| `CashTransactions` | `TransactionTime` | B-Tree | Cierres y auditorías por fecha. |

### 1.3 Implementación

- Crear migraciones EF Core con `migrationBuilder.CreateIndex(...)` para los índices faltantes.
- Para índices parciales, usar `HasFilter` en `OnModelCreating`.
- Ejemplo para `Products`:

```csharp
modelBuilder.Entity<Product>()
    .HasIndex(p => p.SKU)
    .IsUnique()
    .HasFilter("\"IsDeleted\" = false");
```

- Para `Customers` con índice funcional:

```csharp
modelBuilder.Entity<Customer>()
    .HasIndex(c => c.CedulaOrRif)
    .IsUnique()
    .HasDatabaseName("IX_Customers_CedulaOrRif_Lower")
    .HasFilter(null) // No parcial
    .HasOperators("lower");
```

*(Nota: EF Core soporta `HasDatabaseName` y `HasOperators` para índices funcionales en PostgreSQL; verifica la sintaxis exacta de tu versión.)*

### 1.4 Criterios de Aceptación

- [ ] Las consultas de catálogo con 10.000 productos devuelven resultados en < 500 ms.
- [ ] Las búsquedas por SKU y nombre no generan escaneos secuenciales (`EXPLAIN ANALYZE` lo confirma).
- [ ] Los índices se crean mediante migraciones versionadas y se aplican en instalaciones nuevas y actualizaciones.

## 2. Consultas de Solo Lectura con `AsNoTracking`

### 2.1 Objetivo
Reducir el consumo de memoria y el trabajo del Change Tracker en todas las consultas que no necesitan modificar entidades.

### 2.2 Inventario de Consultas

| Servicio | Método | ¿Ya usa AsNoTracking? | Acción |
|----------|--------|------------------------|--------|
| `InventoryService` | `GetProductsPagedAsync` | No | Agregar `AsNoTracking()` |

var query = _context.Products

var sales = await _context.Sales

    .AsSplitQuery()
    .ToListAsync();

## 3. Monitoreo y Corrección de N+1 Queries Residuales

### 3.1 Objetivo
Identificar y eliminar cualquier patrón N+1 en flujos de venta, edición y cierre.

### 3.2 Procedimiento

1. **Activar logging de EF Core** en `appsettings.Development.json`:

```json
{
  "Logging": {
    "LogLevel": {
      "Microsoft.EntityFrameworkCore.Database.Command": "Information"
    }
  }
}
```

2. **Ejecutar flujos críticos** y capturar el número de `Executed DbCommand`:
   - Agregar producto al carrito.
   - Cambiar cantidad.
   - Completar venta con 3 métodos de pago.
   - Recalcular total de una venta con 15 ítems.
   - Listar cuentas abiertas.
   - Cierre diario.

3. **Identificar repeticiones** de consultas sobre la misma tabla en el mismo flujo.

4. **Aplicar técnicas de corrección**:
   - Cargar productos por lote con `GetProductsByIdsAsync`.
   - Cargar métodos de pago con `Dictionary<int, PaymentMethod>`.
   - Usar proyección a DTO con `Select` en lugar de `Include` para listados.
   - Evitar llamadas a `FindAsync` dentro de bucles.

### 3.3 Ejemplo de corrección

**Antes** (N+1 en recálculo de total):

```csharp
foreach (var item in sale.Items)
{
    var product = await _context.Products.FindAsync(item.ProductId);
    // ...
}
```

**Después** (batch):

```csharp
var productIds = sale.Items.Select(i => i.ProductId).Distinct().ToList();
var products = await _context.Products
    .AsNoTracking()
    .Where(p => productIds.Contains(p.Id))
    .ToDictionaryAsync(p => p.Id);
```

### 3.4 Criterios de Aceptación

- [ ] El flujo de venta normal ejecuta menos de 10 consultas SQL (sin contar el guardado final).
- [ ] El recálculo de total para 15 ítems ejecuta exactamente 1 consulta de productos.
- [ ] No existen patrones de `FindAsync` dentro de bucles.

## 4. Caché de Datos Estáticos en Memoria

### 4.1 Objetivo
Reducir consultas repetitivas a la base de datos para datos que cambian con poca frecuencia.

### 4.2 Datos Candidatos a Caché

| Dato | TTL sugerido | Invalidación |
|------|--------------|--------------|
| Métodos de pago activos | 5 minutos | Al crear/actualizar/eliminar método de pago |
| Cliente por defecto (`Consumidor Final`) | 10 minutos | Al actualizar cliente por defecto |
| Tasa BCV del día | 10 minutos | Al actualizar tasa manualmente o por job |
| Configuración de negocio | 15 minutos | Al guardar configuración |

### 4.3 Implementación

1. **Inyectar `IMemoryCache`** en los servicios correspondientes.

2. **Métodos de pago activos** en `PaymentMethodService`:

```csharp
public async Task<List<PaymentMethodDto>> GetActiveMethodsAsync()
{
    var cacheKey = "active_payment_methods";
    if (!_cache.TryGetValue(cacheKey, out List<PaymentMethodDto>? methods))
    {
        methods = await _context.PaymentMethods
            .AsNoTracking()
            .Where(p => p.IsActive)
            .Select(p => new PaymentMethodDto { ... })
            .ToListAsync();

        _cache.Set(cacheKey, methods, TimeSpan.FromMinutes(5));
    }
    return methods!;
}
```

3. **Invalidación** en los métodos de mutación:

```csharp
public async Task CreatePaymentMethodAsync(...)
{
    // ... guardar
    _cache.Remove("active_payment_methods");
}
```

4. **Tasa BCV** en `ExchangeRateService`:

```csharp
var cacheKey = $"bcv_rate_{DateTime.UtcNow:yyyyMMdd}";
if (!_cache.TryGetValue(cacheKey, out decimal rate))
{
    rate = await FetchRateFromBcvAsync();
    _cache.Set(cacheKey, rate, TimeSpan.FromMinutes(10));
}
```

5. **Uso de `CancellationToken`** en las consultas para cancelación rápida.

### 4.4 Criterios de Aceptación

- [ ] Las consultas a métodos de pago no se repiten en cada cobro si ya se cargaron en los últimos 5 minutos.
- [ ] La tasa BCV no se consulta al BCV más de una vez cada 10 minutos por día.
- [ ] Al modificar un método de pago, la caché se invalida inmediatamente.

## 5. Optimización de Paginación y Consultas de Catálogo

### 5.1 Objetivo
Asegurar que el catálogo de productos responda rápido incluso con 10.000 registros, usando paginación server-side eficiente y proyección a DTO.

### 5.2 Implementación

- Ya se dispone de `GetProductsPagedAsync` con paginación y ordenamiento dinámico (implementado en fases anteriores).  
- Verificar que la consulta use `Skip((page - 1) * pageSize).Take(pageSize)` y `CountAsync()` para el total.
- Usar `AsNoTracking` y proyección directa a DTO:

```csharp
var items = await _context.Products
    .AsNoTracking()
    .Where(filter)
    .OrderBy(sortExpression)
    .Skip((page - 1) * pageSize)
    .Take(pageSize)
    .Select(p => new ProductDto { ... })
    .ToListAsync();

var totalCount = await _context.Products.CountAsync(filter);
```

### 5.3 Criterios de Aceptación

- [ ] El catálogo con 10.000 productos responde en < 500 ms con paginación de 25.
- [ ] El ordenamiento y filtrado se ejecutan en el servidor (no en memoria).
