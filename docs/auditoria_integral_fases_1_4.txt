[SEC-01] Ajuste de redondeo arbitrario confiado desde el cliente
--------------------------------------------------------------------------------
- Severidad: CRÍTICA (P0)
- Módulos afectados: Sales.Module / Backend.API
- Ubicación exacta:
  * Sales.Module/Services/SalesService.Checkout.cs: líneas 107-112, 282
  * Backend.API/Controllers/SalesController.Checkout.cs: líneas 126-137
- Código vulnerable:
    if (Math.Abs(roundingAdjustment) > 1000m)
    {
        throw new InvalidOperationException($"Rechazo Defensivo: el ajuste de redondeo...");
    }
    sale.RoundingAdjustment = roundingAdjustment;
- Vector de ataque:
  Un atacante que envía directamente peticiones HTTP a POST /api/sales/{id}/complete
  puede inyectar cualquier valor entre -1000 y +1000 en roundingAdjustment. El backend
  nunca valida que este valor coincida con la diferencia aritmética real entre lo
  cobrado y el total de la orden. Esto altera los libros fiscales, el balance diario
  y el arqueo de caja sin disparar alertas.
- Corrección exigida:
  El backend debe recalcular el ajuste de redondeo de forma determinista contra los
  pagos reales registrados en la base de datos y descartar cualquier valor del payload:
    decimal expectedRounding = remainingBalanceUsd <= 0.01m 
        ? PricingCalculator.RoundToDigital(sale.Payments.Sum(p => p.AmountBsS) - sale.TotalBsS) 
        : 0m;
    sale.RoundingAdjustment = expectedRounding;

[SEC-02] Bypass de autorización de precios vía productos de adelanto de efectivo
--------------------------------------------------------------------------------
- Severidad: CRÍTICA (P0)
- Módulos afectados: Sales.Module
- Ubicación exacta:
  * Sales.Module/Services/SalesService.HoldOrders.cs: líneas 338-348
  * Sales.Module/Services/SalesService.Checkout.cs: línea 298
- Código vulnerable:
    if (!product.IsCashAdvance && reqItem.UnitPrice > 0 && reqItem.UnitPrice != effectivePrice && !isPriceOverrideAuthorized)
    {
        throw new UnauthorizedAccessException($"Modificación de precio no autorizada...");
    }
    decimal unitPriceUsd = reqItem.UnitPrice > 0 ? reqItem.UnitPrice : effectivePrice;
- Vector de ataque:
  Al modificar ítems de una venta en espera (PUT /api/sales/{id}/items), la cláusula
  !product.IsCashAdvance desactiva la validación de autorización de precio. Un cajero
  puede agregar un producto de adelanto con un precio arbitrario ($0.01 o $10,000).
  Al completarse la venta, la línea 298 de SalesService.Checkout.cs ignora la deducción
  de inventario (if (product.IsCashAdvance) continue;), permitiendo registrar
  transacciones fraudulentas sin autorización de un supervisor.
- Corrección exigida:
  Prohibir la inclusión de productos de adelanto en AddItemAsync y UpdateSaleItemsAsync.
  Los productos IsCashAdvance solo deben gestionarse mediante CashAdvanceCoordinator.

- Ubicación exacta:
  * Backend.API/Controllers/CashDrawerController.cs: líneas 324-326
  * Sales.Module/Services/CashAdvanceCoordinator.cs: líneas 134, 147

        ? request.UserName

[SEC-05] Fuga de hashes y sellos de seguridad por falta de [JsonIgnore]
--------------------------------------------------------------------------------
- Severidad: ALTA (P1)
- Módulos afectados: Core / Backend.API
- Ubicación exacta:
  * Backend.API/Startup/ServiceCollectionExtensions.cs: líneas 166-170
  * Core/Entities/User.cs: líneas 16, 24
- Código vulnerable:
    // ServiceCollectionExtensions.cs:
    x.JsonSerializerOptions.ReferenceHandler = System.Text.Json.Serialization.ReferenceHandler.IgnoreCycles;
    // User.cs:
    public string PasswordHash { get; set; } = string.Empty;
    public string SecurityStamp { get; set; } = Guid.NewGuid().ToString("N");
- Vector de ataque:
  ReferenceHandler.IgnoreCycles silencia las excepciones de ciclos y permite serializar
  entidades completas. Al carecer de [JsonIgnore], cualquier endpoint o proyección
  accidental que retorne la entidad User expondrá los hashes bcrypt y los sellos
  de seguridad en la respuesta JSON.
- Corrección exigida:
  Agregar [System.Text.Json.Serialization.JsonIgnore] a PasswordHash y SecurityStamp
  en User.cs y asegurar mediante pruebas de arquitectura que ningún controlador
  retorne entidades del dominio.

[PERF-01] Bucle N+1 crítico en matching de facturas de proveedores
--------------------------------------------------------------------------------
- Severidad: ALTA (P1)
- Módulos afectados: Inventory.Module
- Ubicación exacta:
  * Inventory.Module/Services/SupplierInvoiceService.Staging.cs: líneas 40-47
  * Inventory.Module/Services/SupplierInvoiceService.Matching.cs: líneas 37-117
- Código vulnerable:
    foreach (var line in lines)
    {
        var match = await MatchProductAsync(supplier.Id, line, similarityThreshold, cancellationToken);
        invoice.Lines.Add(CreateStagedLine(line, match, unitCostUsd, request.OcrSourced));

- Costo computacional:

  del bucle (ToDictionaryAsync) y evaluar las coincidencias exactas en memoria,
  dejando la búsqueda difusa solo como fallback para los ítems no emparejados.

--------------------------------------------------------------------------------
- Severidad: MEDIA (P2)
- Módulos afectados: Backend.API (Controladores)
- Ubicación exacta:
  * Backend.API/Controllers/SalesController.Checkout.cs: líneas 88-89, 173-174, 216-217

  directamente los métodos asíncronos canónicos con CancellationToken.

[CLEAN-04] Fuga del motor de liquidación y redondeo en controlador HTTP
--------------------------------------------------------------------------------
- Severidad: CRÍTICA (P0)
- Módulos afectados: Backend.API / Sales.Module
- Ubicación exacta:
  * Backend.API/Controllers/SalesController.Checkout.cs: líneas 29-72
- Principio violado: Single Responsibility Principle (SRP), Domain-Driven Design (DDD).
- Diagnóstico técnico:
  El controlador HTTP implementa directamente el cálculo financiero de pagos mixtos,
  umbrales de liquidación (remainingUsd <= 0.05m), reglas fiscales de redondeo

- Reestructuración requerida:
  Extraer la lógica a un servicio de dominio en Sales.Module (ej. ICheckoutCalculationService).
  El controlador solo debe recibir la petición y delegar al servicio.

[SRE-01] Deadlock circular AB-BA en deducciones multiproducto
--------------------------------------------------------------------------------
- Severidad: CRÍTICA (P0)
- Módulos afectados: Inventory.Module
- Ubicación exacta:
  * Inventory.Module/Services/InventoryService.StockDeduction.cs: líneas 60-93
- Código vulnerable:
    foreach (var item in itemList) // Itera en el orden arbitrario enviado por el cliente
    {
        int rows = await _context.Products
            .Where(p => p.Id == targetProductId && ...)
            .ExecuteUpdateAsync(...); // Bloqueo exclusivo de fila en PostgreSQL
    }
- Edge case descubierto:
  Si el Cajero 1 vende [Producto A, Producto B] y el Cajero 2 vende [Producto B, Producto A]
  simultáneamente, las transacciones adquieren bloqueos cruzados en PostgreSQL,
  desencadenando un deadlock (código de error 40P01). Al no ser reintentable por
  NpgsqlRetryingExecutionStrategy dentro de BeginTransactionAsync, la venta falla
  con HTTP 500 y el checkout aborta abruptamente.
- Solución arquitectónica:
  Ordenar deterministamente las deducciones por ProductId ascendente antes de bloquear:
    var consolidated = itemList
        .GroupBy(i => ResolveTargetProductId(i))
        .Select(g => new StockDeductionRequest(g.Key, g.Sum(x => x.QuantityChange), ...))
        .OrderBy(i => i.ProductId)
        .ToList();

[SRE-02] Faltante de idempotencia en ítems, egresos y cierres de caja
--------------------------------------------------------------------------------
- Severidad: CRÍTICA (P0)
- Módulos afectados: Backend.API / Sales.Module
- Ubicación exacta:
  * Backend.API/Controllers/SalesController.cs: línea 123 (POST /api/sales/{id}/items)
  * Backend.API/Controllers/CashDrawerController.cs: línea 134 (POST /api/cashdrawer/transaction)
  * Backend.API/Controllers/DailyClosureController.cs: línea 48 (POST /api/dailyclosure)
  * Sales.Module/Services/SalesService.cs: líneas 283-297
- Escenario de fallo:
  1. Adición de ítems: Un microcorte en la red inalámbrica tras guardar el ítem pero
     antes del HTTP 200 causa un reintento del cliente. SalesService:286 ejecuta
     existingItem.Quantity += quantity, duplicando la cantidad vendida.
  2. Egresos de caja: Un reintento al registrar un egreso de $50 USD inserta dos
     transacciones de gasto, descontando $100 USD del libro contable.
  3. Cierre fantasma: Un reintento en el cierre diario se ejecuta contra la sesión
     renovada (con 0 ventas), reportando un falso descuadre contable masivo.
- Solución arquitectónica:
  Extender el middleware o filtro de acción [RequireIdempotencyKey] a todos los
  endpoints mutacionales. En POST /api/sales/{id}/cancel, retornar HTTP 200
  idempotente si la venta ya estaba cancelada, en lugar de lanzar 409 Conflict.

- Impacto SRE:
  Bajo concurrencia (ej. 50+ peticiones concurrentes registrando auditorías o fallos),
  todos los hilos de ASP.NET Core se bloquean en el mutex global esperando escrituras
  en disco. Esto agota el ThreadPool, introduce picos severos de latencia y degrada
  la capacidad del sistema. Además, el uso de cadenas interpoladas ($"...") impide
  la indexación estructurada en motores de observabilidad (Seq, Elasticsearch).
- Solución arquitectónica:
  Reemplazar el logger estático por Microsoft.Extensions.Logging respaldado por
  Serilog con sink asíncrono no bloqueante (Serilog.Sinks.Async) y plantillas
  de mensajes estructurados (clave-valor).
